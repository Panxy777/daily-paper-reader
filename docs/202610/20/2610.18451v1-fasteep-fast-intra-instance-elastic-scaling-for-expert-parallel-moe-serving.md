## 摘要
大规模专家并行（EP）已成为生产环境中混合专家（MoE）模型的标准部署配置。同时，大语言模型工作负载的高度动态性要求服务提供商持续调整服务容量以匹配波动的需求。MoE 服务的扩缩容无法仅通过简单增加或移除服务实例来高效实现；相反，它通常需要调整现有实例内的 EP 组大小，我们将其称为实例内扩缩容。现有推理引擎主要依赖实例级扩缩容，这会销毁并重建整个服务实例，带来巨大的扩缩容开销。我们提出 FastEEP（快速弹性专家并行），一种基于部分复用原则的面向 MoE 服务的快速实例内扩缩容系统。FastEEP 通过将可复用执行结构与当前 EP 配置激活的资源分离，在 worker 执行、GPU 内存和通信之间复用现有运行时状态。这种分离实现了协调的资源回收与重配置，同时保留重建代价高昂的状态，从而无需完整实例拆除与重建即可实现快速 EP 扩缩容。我们的评估表明，在不同模型上，FastEEP 的扩缩容速度比现有基于 vLLM 的方法快 4.5 倍至 11.7 倍，从而实现 MoE 服务高效、细粒度的扩缩容。

## Abstract
Large-scale expert parallelism (EP) has become the standard deployment configuration for Mixture-of-Experts (MoE) models in production. Meanwhile, the highly dynamic nature of LLM workloads requires providers to continuously adjust serving capacity to match fluctuating demand. Scaling MoE serving cannot be efficiently achieved by simply adding or removing serving instances; instead, it often requires resizing the EP group within an existing instance, which we refer to as intra-instance scaling.Existing inference engines primarily rely on instance-level scaling, which destroys and reconstructs entire serving instances, incurring substantial scaling overhead.   We present FastEEP (Fast Elastic Expert Parallel), a fast intra-instance scaling system for MoE serving based on the principle of Partial Reuse. FastEEP reuses existing runtime state across worker execution, GPU memory, and communication by separating reusable execution structures from the resources activated by the current EP configuration. This separation enables coordinated resource reclamation and reconfiguration while preserving costly-to-reconstruct state, allowing fast EP scaling without full instance teardown and reconstruction. Our evaluation shows that FastEEP achieves 4.5x--11.7x faster scaling than the existing vLLM-based approach across different models, enabling efficient, fine-grained scaling of MoE serving.

### 1. 核心问题与整体含义

- **背景**：MoE 模型在生产中普遍采用专家并行（EP）部署，EP 规模常达数十至数百 GPU。EP 越大，单 GPU 专家权重冗余越少，可腾出更多 HBM 给 KV cache；但实例粒度也随之变粗，扩缩容灵活性下降。
- **核心问题**：LLM 负载高度动态，而现有推理引擎主要做**实例级扩缩容**——销毁并重建整个服务实例。对于宽 EP MoE 实例，这会带来数十秒级停机、通信组重建、CUDA Graph 重捕获、worker 重启等巨大开销。
- **需求**：需要**实例内 EP 动态扩缩容**，且满足三个条件：  
  - **细粒度**：以单 GPU 为粒度调整，而非整实例；  
  - **快速**：扩缩容时间应短于流量波动持续时间；  
  - **可逆**：扩缩容后能快速回收/恢复资源，避免反复重建。
- **本质矛盾**：现有系统把“活跃资源”与“初始化运行时状态”绑定在同一生命周期中，导致改变 EP 度时必须破坏通信域、虚拟地址、CUDA Graph、worker 上下文等昂贵状态。FastEEP 的整体含义是：**通过部分状态复用，把 MoE 服务的扩缩容从“重建实例”转变为“切换活跃配置”**。

### 2. 方法论

#### 2.1 核心思想：Partial Reuse（部分复用）

- 将服务状态分为两类：  
  - **持久/可复用结构**：worker 进程、执行器、编译内核、CUDA 上下文、父通信域、虚拟地址、CUDA Graph 可执行体、控制面状态等；  
  - **随当前 EP 配置变化的活跃资源**：活跃 rank 集合、专家到物理槽映射、物理页驻留、请求路由、NIXL 可达性等。
- 扩缩容时只改变后者，保留前者；对必须释放的 GPU 资源，采用“**保留逻辑身份、释放物理资源**”的方式，并在扩回时原位恢复。

#### 2.2 通信复用：父域 + 子组 + 掩码

- **NCCL 集合通信**：启动时创建覆盖最大 worker 集的父通信域，保留全局 rank 空间、bootstrap 关系和参考计数资源；每次 resize 通过 **NCCL communicator split** 派生仅含活跃 rank 的子组，避免非活跃 rank 阻塞集合通信。
- **EP All-to-All / 点对点通信**：使用 **NIXL mask** 表示活跃 rank 可达性；scale-down 时在专家副本就绪后屏蔽目标 rank，scale-up 时在缓冲和端点就绪后再解除屏蔽。
- **统一提交**：NCCL 子组、NIXL mask、专家逻辑到物理槽映射、请求路由在同一个安全点一起发布，保证各 rank 对活跃集合的视图一致。
- 父通信域的数据面缓冲可卸载到 pinned host memory，仅保留元数据和控制面状态；文中称父域总开销小于 300 MB。

#### 2.3 显存复用：稳定虚拟地址 + 按语义恢复

- 使用 **CUDA Virtual Memory Management（CuMem）** 为共享权重、专家权重、KV cache、CUDA Graph 缓冲分别建立内存池。
- scale-down 时 **unmap 并释放物理页，但保留虚拟地址、张量元数据和对象引用**；scale-up 时在相同虚拟地址映射新页，从而保持内核参数、张量指针和分配器对象有效。
- 恢复策略按数据语义区分：  
  - **复制权重/非专家权重**：从活跃 rank 经 NVLink 设备到设备复制回原地址；  
  - **专家权重**：先重算目标专家布局，缺失专家复制到剩余活跃 worker 的空闲槽；  
  - **KV cache**：逐块选择“丢弃后重算 / NVLink 异步迁移 / swap 到 pinned host 后重载”；  
  - **CUDA Graph 缓冲**：捕获时分配到专用 graph 池，sleep 时备份并释放物理页，wake 时同地址恢复，直接 replay 而无需重捕获；  
  - **通信缓冲**：遵循“先撤销可达性再释放内存，先恢复内存再授予可达性”。
- 目标是最小化主机内存换恢复延迟，同时避免重建执行上下文。
