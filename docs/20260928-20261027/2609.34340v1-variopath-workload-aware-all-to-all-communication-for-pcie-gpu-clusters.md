## 摘要
AlltoAllv 通信是分布式大模型推理中的关键原语，尤其在混合专家（MoE）模型中更是如此。随着 PCIe GPU 系统因高性价比推理而被越来越多地采用，AlltoAllv 在这类系统上的性能愈发重要。由于缺乏专用的 scale-up 互连（如 NVLink 或 Infinity Fabric），PCIe GPU 系统需通过 PCIe 层级承载节点内和节点间流量，并发传输会争用 PCIe 链路带宽。这种链路争用，加之流量分布偏斜和动态流量需求，使得高效的 AlltoAllv 调度颇具挑战。现有方法要么不适合 PCIe GPU 系统，要么产生大量调度合成开销，降低其在实际部署中的实用性。我们提出 VarioPath，一种面向 PCIe GPU 系统的高效 AlltoAllv 调度框架。它将离线拓扑感知分析器与在线需求感知调度器相结合。分析器将无争用的传输模式记录为 AlltoAllv 通道，并利用拓扑对称性构建紧凑目录以支持高效搜索。在线调度器将每次 AlltoAllv 调用的需求分解到一系列通道上，从而适应快速变化且偏斜的流量，同时保持较低的规划开销。在四个平台（最多 256 块 GPU）上的评估显示，AlltoAllv 平均相比 FAST 加速 5.88 倍，相比 DeepEP 加速 1.72 倍。端到端实验表明，VarioPath 将 Qwen3 推理延迟最多降低 27.2%，将 Wan2.1 生成延迟降低 6.1%。

## Abstract
AlltoAllv communication is a critical primitive in distributed large-model inference, particularly for mixture-of-experts (MoE) models. The growing adoption of PCIe GPU systems for cost-efficient inference makes AlltoAllv performance on these systems increasingly important. Without a dedicated scale-up interconnect (e.g., NVLink or Infinity Fabric), PCIe GPU systems carry both intra-node and inter-node traffic through the PCIe hierarchy, where concurrent transfers can contend for PCIe link bandwidth. This link contention, compounded by skewed traffic distributions and dynamic traffic demand, makes efficient AlltoAllv scheduling challenging. Existing approaches are either poorly suited to PCIe GPU systems or incur substantial schedule synthesis overhead that reduces their practicality in real-world deployments.   We present VarioPath, an efficient AlltoAllv scheduling framework for PCIe GPU systems. It combines an offline topology-aware analyzer with an online demand-aware scheduler. The analyzer records contention-free transfer patterns as AlltoAllv channels and exploits topology symmetry to build a compact catalog for efficient search. The online scheduler decomposes each AlltoAllv invocation's demand across a sequence of channels, adapting to rapidly changing and skewed traffic while incurring low planning overhead. Evaluation on four platforms (up to 256 GPUs) shows average AlltoAllv speedups of 5.88x over FAST and 1.72x over DeepEP. End-to-end experiments show that VarioPath reduces Qwen3 inference latency by up to 27.2% and Wan2.1 generation latency by 6.1%.

## 1. 核心问题与研究动机

- **背景**：AlltoAllv 是分布式大模型推理的关键通信原语——在专家并行（EP）中负责 token 派发/回收，在序列并行（SP）中负责 attention 张量重分布。MoE 每层都会依据路由结果重新生成一个 AlltoAllv 需求矩阵，单层执行常在 1 ms 以下，因此调度器必须在同样短的时间尺度上完成适配。
- **平台特殊性**：PCIe GPU 系统（如阿里、字节、Cloudflare 部署的 T4/L40S 集群）没有 NVLink/NVSwitch 这类专用 scale-up 网络，节点内 P2P 与经 NIC 的节点间流量**共用同一套 PCIe 层级**，且拓扑多为非 Clos，无法保证无阻塞。
- **三重挑战**：
  1. **链路争用**：端点不相交（endpoint-disjoint）的逻辑传输仍可能在共享 PCIe 链路上汇聚，形成热点，同时其他路径空闲。
  2. **流量偏斜**：部分 rank 对的数据量远大于其他，导致慢路径拖尾（communication tail），决定整个调用的完成时间。
  3. **动态需求**：静态调度不可行，需按每次调用实时适配。
- **现有方案不足**：
  - NCCL / MSCCL：运行时开销低，但路径在 communicator 建立时固定，无法随需求变化。
  - FAST / DeepEP：依赖额外节点内转发来均衡流量，在 PCIe 系统上这些转发与 NIC 流量争用同一 PCIe 资源，**反而加剧争用**。
  - TACCL / TE-CCL / SCCL 等 MILP 合成：需数分钟到数小时，无法每次调用重跑。
  - Blink / BlueConnect / TCCL：面向 PCIe 但主要针对 AllReduce/AllGather 等规则集合通信，多为 ring 类算法，不直接适用于 AlltoAllv。
- **整体含义**：论文试图在"拓扑感知"与"需求自适应"之间找到一个低开销的折中，使 PCIe GPU 集群上的 AlltoAllv 调度既无链路争用、又能跟上逐层变化的需求。

## 2. 方法论

### 2.1 核心思想（关键洞察）

- **拓扑稳定、需求易变**：无争用的并发传输模式只由拓扑决定，可离线枚举并复用；需求只需在线表示为这些模式的线性组合。
- 引入 **channel（通道）** 抽象：一个 channel = 一个"无争用并发传输模式"（一组 peer 配对 + 每对选定的一条物理路径）。
- 引入 **activation（激活）**：channel + 每条 lane 的数据量 = 一个 AlltoAllv 阶段；一次调用的调度 = 一串 activation，其服务量之和等于需求矩阵。
- 由此把"每次调用重复组合搜索拓扑"替换为"离线建目录 + 在线轻量分解"。

### 2.2 调度模型与形式化

- 需求矩阵 $D \in \mathbb{Z}_{\ge0}^{N\times N}$，$D_{ii}=0$；每对 $(i,j)$ 有候选路径集 $P_{ij}$，路径 $p$ 有速率 $bw(p)$ 与占用的有向资源集 $L(p)\subseteq U$（仅建模共享 PCIe 链路与 NIC 侧资源，端点本地链路因排列约束不会同向复用而排除）。
- **Channel** $C=(\pi, p)$：$\pi$ 是 $V$ 上的无自环排列（每 rank 恰好一条出 lane、一条入 lane，天然避免端点扇入/扇出）。
- **可行性**：任一建模资源至多被一条选中路径占用（式 1）。同向共享链路在通道内被保守地设为互斥（因并发会使速率依赖流量）。
- **Activation** $E=(C,x)$：给每条 lane 赋非负整数流量 $x_i$，$X(E)_{i,\pi(i)}=x_i$，其余为 0。
- **调度有效性**：$\sum_k X(E_k)=D$。
- **优化目标**（式 2）：最小化 $\sum_k \left(\lambda + \max_i \frac{x_{k,i}}{bw(p_{k,i})}\right)$，即"每阶段固定开销 + 最慢 lane 时间"之和，体现"缩短拖尾"与"减少阶段数"的权衡。

### 2.3 离线：拓扑感知的通道分析（Algorithm 1）

- **拓扑抽象**：把 $N=Gg$ 个 rank 划分为 $G$ 个交换机本地、拓扑等价的 rank 组 $V_a$（每组 $g$ 个）；组级路径实例 $r\in R_{ad}$ 只记录共享资源路由，端点本地 GPU–交换机连接留待绑定。
- **通道形状（shape）** $M\in\mathbb{Z}_{\ge0}^{G\times G}$：$M_{ad}$ 为 $V_a\to V_d$ 的 lane 数；可行形状需行/列和均为 $g$（式 3），保证每组恰好 $g$ 出 $g$ 入。
- **通道族（family）** $B$：在形状基础上选定具体的组级路径实例，要求每个组对恰好选 $M_{ad}$ 个（形状一致），且所选实例资源两两不交（式 4）。存入桶 $B[M]$；$B[M]\neq\varnothing$ 即形状可实现（论文给出 $M_1$ 不可实现、$M_2$ 由 $B_1$ 实现的例子）。
- **端点绑定**：把族中每个实例一对一映射到组内 GPU 对 $(i,j)\in\Gamma_{ad}$，即得到一个具体 channel；组等价假设保证 $L(p)=L(r)$、$bw(p)=bw(r)$。
- **DFS 构造目录树**：按固定顺序做剪枝二叉搜索；`CANADD` 检查资源不交与组度约束，`SUFFIXOK` 判断剩余实例能否填满各组 $g$ 个出入槽位，`COMPLETE` 时按组对计数归入对应 $B[M]$。
- **两级支配剪枝**：`PRUNEPATHS` 删除被同组对更优路径（资源子集且速率不低于）支配的实例，降低分支因子；`PRUNEFAMILIES` 删除完全重复及同形状内被支配的族，减少暴露给在线调度的候选数。
- 最坏复杂度 $O(2^{|R|})$，但实际被资源检查、后缀剪枝与支配过滤大幅压缩；目录每机器配置构建一次并复用。
