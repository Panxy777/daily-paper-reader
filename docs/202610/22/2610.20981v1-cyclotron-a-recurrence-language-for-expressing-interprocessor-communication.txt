Abstract 

We present Cyclotron, a compiler that expresses streaming dataflow algorithms using recurrence equations, which are then compiled to distributed topologies of interlinked pro-cessors. Our compiler lowers a language of recurrences over logical iteration spaces into per-processor programs of sends, receives, and computations. In these recurrences, data ac-cesses are not limited to external accesses to memory; data can live separately on the iteration space itself, allowing internal points to communicate values directly with other points. Users specify this communication directly in the re-currence language, which allows them to express various communication patterns such as a nearest-neighbor systolic exchange, a one-to-all broadcast, a bidirectional split ring, or an asymmetric and piecewise broadcast pattern, which are often not supported by standard distributed linear alge-bra libraries. These recurrences describe the algorithm and communication independently of how they map onto the hardware. A programmer then chooses which dimensions execute across processors and which execute over time, with-out rewriting the entire program. Users only specify data dependencies across the iteration space, and the compiler safely generates a program, per process, with correct place-ment of both communication and computational operators according to the chosen space–time mapping. We evalu-ate distributed matrix multiplication, TRSM, Cholesky, and fused Cholesky–TRSM on up to 16 CPU nodes and 16 GPUs, comparing against ScaLAPACK, SLATE, and cuSolverMp. Cyclotron is competitive with and often outperforms these hand-optimized libraries; for Cholesky, the best communica-tion strategy changes with problem size and architecture. 

1 Introduction 

Generations of architectural improvements have widened the gap between the cost of data movement and the cost of computation. Performance optimization is now dominated by minimizing memory traffic and network communication on distributed architectures. Extracting performance from such hardware is largely a matter of orchestrating how data moves through that fabric: laterally between PEs, and tem-porally as values are retained in fast memory across steps. Yet the dominant abstractions for programming these ma-chines do not represent data movement beyond memory loads/stores. In tensor algebra notation, loop-based IRs, and polyhedral representations, every data access is a tensor access—logical reads from or writes to memory locations. Such a program says what value each statement consumes, but not how or where that value travels between processors or across time. The movement is left implicit, to be recovered by dependence analysis and then realized by a lowering pass. In computational problems where communication is a pri-mary bottleneck, such as in distributed linear algebra (e.g., matrix multiplication), tensor algebra, and recurrences, the best communication policy can vary with input size, tile size, interconnect, and processor architecture. Yet standard dis-tributed libraries like ScaLAPACK [7] or SLATE [10] either hard-code communication policies or expose only a small set of predefined options. Consequently, the best commu-nication schedule for a particular problem and architecture may not be available to the programmer. Compiler frameworks avoid pitfalls of writing distributed code by hand, which is error-prone and can lead to indefinite hangs from mismatched or incorrectly ordered communica-tion, while also being difficult to optimize (e.g., overlapping communication with computation). Polyhedral frameworks have made important steps forward in modeling relation-ships between iteration spaces and memory accesses. Exist-ing polyhedral frameworks, like AutoSA [37] for systolic-array synthesis and AlphaZ for distributed-memory code generation,[39] lower dependencies into nearest-neighbor transfers; both therefore effectively commit to a systolic realization of communication. As a result, alternative real-izations of the same logical dependence, such as a one-to-all broadcast, a tree-broadcast, or heterogeneous combinations of broadcast and forwarding, are not supported. This limitation stems from what the user program leaves unspecified. There are typically many ways to realize data movement, but without user input the compiler must choose among them. For example, AutoSA and AlphaZ only generate code where communication is limited to between neighboring PEs. This can leave performance on the table when a different commu-nication strategy better matches the problem size or target architecture. Stellar [12], a framework for spatial accelerator design, allows users to specify dataflow and lets iteration-space points receive data from neighbors, supporting systolic patterns, but does not generalize beyond them. This paper presents the Cyclotron compiler that makes the communication schedule a first-class part of the input program. The program can express many different commu-nication patterns as recurrence equations. These include systolic exchanges, one-to-all broadcast, tree-broadcast, bidi-rectional split rings, or asymmetric, piecewise combination of communication policies, in which different subdomains of a program and processor grid carry different communication policies. A user can specify that a data tile travel via nearest-neighbor hops in one part of the processor grid, via a tree broadcast in other parts, and bidirectionally in another. In Cyclotron, the programmer writes computation as a system of recurrences that can index into tensors that live on the iteration space in addition to tensors that live in mem-ory, thus controlling data movement. Figure 1 illustrates the 3D iteration space of a matrix multiply, contrasting a pro-gram where data is accessed exclusively from tensors with two different programs where data is also obtained from points in the iteration space. What differs is how each value is obtained: directly from the tensor, from a neighboring iteration-space point, or from a boundary point via broad-casts. In Cyclotron, a value on the iteration space is named not only by which tensor element it is (e.g., 𝐴 𝑖 𝑗 ) but by the point in the iteration space at which it lives, written (𝑖, 𝑗, 𝑘 )𝐴 .Movement, like the systolic transfer (𝑖, 𝑗, 𝑘 )𝐴 ← ( 𝑖, 𝑗 −1, 𝑘 )𝐴 ,is expressed in the same coordinate system as computation: a recurrence relating a value at one point to another point is 

a data movement. A separate per-dimension annotation de-clares whether each dimension is spatial (movement between PEs) or temporal (retention across steps). Data movement is not limited to nearest neighbors, and because the recur-rence is written independently of this annotation, the same program can be used to generate different spatial mappings. The user’s input recurrences are unordered. The order-ing of compute and communication operations depends on which dimensions are mapped in space and time. Cyclotron’s dependency algorithm uses this mapping to derive correct orderings, relieving users of the need to manually sequence such operations and avoiding indefinite waits caused by in-correct communication ordering. These recurrences are compiled to distributed code through a fixed pipeline: a space–time mapping folds the iteration space and inserts a temporal loop. Our dependency-management algorithm resolves data dependencies into coupled sends and receives. Synchronization-aware control flow is inserted according to the target protocol. A final pass can apply a block-cyclic decomposition and deduplicate communication. Cyclotron lets programmers explore communication strate-gies with minimal program changes. The resulting code is competitive with, and often outperforms, expert-tuned li-braries. We make the following contributions: 

• A recurrence-based programming model where com-munication is a first-class programmable concern, sep-arate from computation and space–time mapping, en-abling programmers to express and compose systolic, broadcast, ring, tree, and heterogeneous piecewise communication strategies. 

• A dependency-management algorithm that uses the chosen space–time mapping to order computation and communication from unordered recurrences 

• A complete compilation pipeline integrating the de-pendency algorithm with transformations that han-dle synchronization, block-cyclic decomposition and communication deduplication, generating efficient dis-tributed programs. By exploring different communication schedules, we demon-strate 1 .7–1 .8× over ScaLAPACK for matrix multiply. For Cholesky on up to 16 CPU nodes, we observe 1 .34–1 .68 ×

speedup over ScaLAPACK on CPUs and 1 .01 −1.24 × speedup over SLATE on GPUs (which uses CPU-side communica-tion), and 1.12–1.28 × speedup over cuSolverMp, Nvidia’s optimized multi-GPU vendor library, when only using di-rect GPU-GPU communication. We demonstrate benefits of simultaneously composing different space–time mappings and how Cyclotron natively fuses kernels.

Different processors execute different sequences of these operations depending on their position in the processor grid and the current step of the factoriza-tion. Moreover, these operations depend on values produced elsewhere in the grid, and those dependences can be realized using different communication strategies; communication is not simply a uniform pattern of nearest-neighbor shifts. The computation is load–imbalanced, in which critical paths oc-curring in certain portions of the grid asymmetrically affect work on downstream processors. Figure 2 shows two loop-based formulations of blocked Cholesky. Even in the serial, non-distributed case, the loop form is coupled to the dependencies among the four kernels. In other words, changing the loop ordering requires more than merely permuting loop headers, as one can for perfectly nested computation such as matrix multiplication. It changes loop bounds, the number and placement of inner loops, the ordering of kernel calls, and their indexing. In loop–based spatial frameworks, loop dimensions/nesting–order are also used to determine which parts of the computation execute across processors and which execute over time. Changing the space–time mapping can therefore require restructuring the program rather than simply changing a mapping decision. 3 Notation 

Recurrences and tensor algebra have traditionally been de-fined over indexed tensors [15, 33, 34, 36]. Cyclotron aug-ments this with recurrences over iteration spaces . In conven-tional recurrence and tensor-algebra equations, each tensor access ( 𝐴 𝑖 𝑗 , or A[i][j] ) denotes a logical access to a memory hierarchy. This model maps well to von Neumann programs on a single processor, but lacks any mechanism for describ-ing data that propagates through time or across processors as every data reference is a tensor access. Cyclotron’s notation describes both computation and com-munication. First, computations are defined as recurrences over an iteration space (Section 3.1). This way, data may live on the iteration space itself, in addition to living in exter-nal tensors. Second, communication patterns are specified in that same language (Section 3.3), as a transfer between two points in the iteration space: a systolic relay, a broadcast, or a piecewise hybrid of the two is just another recurrence, distinguished only by the shape of its coordinate expressions. Figure 1 illustrates this dichotomy of accessing data from memory versus the iteration space. 

3.1 Defining Recurrences over Iteration Spaces 

In a spatial program, data moves laterally between processors and can be retained in fast memory across time. If processors are assigned distinct portions of a program’s iteration space, then dataflow across the iteration space corresponds directly to dataflow between processors, or to dataflow across time.

In loop-based dataflow languages every data access is a tensor access, so the language can detect that a value must be broad-cast across the iteration space but has no notion of how or where the data moves; in Cyclotron the movement and the computation it serves are expressed in one grammar. Cyclotron specifications are loop-free and unordered. All iteration-space indices are in scope at every recurrence, and no loop order is imposed. The loop-order coupling dissected in Section 2 (e.g. the 𝑖 𝑗𝑘 vs 𝑘𝑖 𝑗 Cholesky loops) is not rele-vant with recurrences. A separate space–time map linearizes the dependence relation, while remaining separate from the equations to avoid overspecializing programs and to promote program reuse.

3.3 Specifying Communication 

Because movement is written as coordinate offsets, a commu-nication pattern is determined by the recurrence’s coordinate expressions: which coordinates carry offsets, and whether the source point is named relative to the consumer or ab-solutely. Figure 6 illustrates four example shapes over an iteration space (𝑖, 𝑗 ) with 𝑖 spatial and 𝑗 temporal. We de-scribe four common patterns. 

Systolic relay. A relative source such as 

(𝑖, 𝑗 )𝑋 ← ( 𝑖 − 1, 𝑗 )𝑋 (1) forwards values one processor at a time. Offsets need not be unit length; unit offsets denote nearest-neighbor shifts. 

Broadcast. An absolute or gimbal-locked source such as 

(𝑖, 𝑗 )𝑋 ← ( 𝑗, 𝑗 )𝑋 (𝑖 > 𝑗 ), (2) causes many consumers indexed by 𝑖 to read the same source point where 𝑖 == 𝑗 . 4.4 Minimizing communication 

Triangular iteration spaces like Cholesky’s are load imbal-anced under a one-tile-per-processor mapping. Cyclotron therefore supports a 2D block-cyclic decomposition, which maps the virtual processor grid onto a smaller physical grid in round-robin fashion. This both balances work and exposes redundant communication. If several virtual processors on the same physical processor require the same tile from an-other processor, only one network receive is necessary and the remaining consumers/virtual processors can reuse the same local copy. Cyclotron applies this decomposition in two phases. The first is a post-processing pass that wraps each processor program with loops over its resident virtual processors and inserts the required modulo and guard logic. Afterwards, the generated code is specialized to each physi-cal processor; control flow is removed, as well as redundant sends, receives, and guards. The resulting per-processor pro-grams remain small because each generated operation corre-sponds to a coarse-grained tiled computation. An alternative is to eliminate redundant communication with a runtime cache, but this introduces additional runtime overhead. 

5 System and Implementation 

The Cyclotron front-end language and compiler are imple-mented in Python, while the runtimes that execute generated programs are native C++ and Rust. Cyclotron has three back-ends: a C++ backend for CPU clusters, a C++ backend for GPU clusters, and a Rust backend built with DAM [42], a framework for modeling dataflow architectures in which PEs communicate over channels. Each backend interprets the same portable Protobuf program, allowing a generated exe-cutable to run unchanged across backends. The Rust backend is used primarily for simulation. It reproduces the commu-nication behavior of the cluster backends, including sim-ulated MPI protocol behavior, without requiring payloads. This allows Cyclotron to detect indefinite hangs and model communication and kernel latencies without executing on a cluster. The simulator can also execute with real payloads and produce correct results, although this mode is disabled by default because it runs on a single processor. The Rust backend can be used to simulate spatial-processors composed of interlinked PEs; this exploration is future work.

6.3 Fusion 

Each PE in a Cyclotron program eagerly executes an opera-tion as soon as its dependencies are satisfied. Consequently, running subsequent kernels does not introduce a global bar-rier between them: operations from the second kernel can begin before the first kernel has completed across all PEs. The preceding ping-pong TRSM experiment demonstrated this effect across successive instances of the same kernel, where pipeline imbalances in adjacent solves overlap natu-rally without an explicit user-directed fusion primitive. The same mechanism applies across different kernels; we also execute a Cholesky followed by a multi-right-hand-side triangular solve. Table 3 reports this experiment on four CPU nodes in both block-cyclic and non-block-cyclic regimes. In the non-block-cyclic configuration, Cholesky is load-imbalanced, and processors in earlier rows and columns of the processor grid finish their assigned factorization work substantially earlier than others. Because Cyclotron executes operations as soon as their dependencies are satisfied, por-tions of the subsequent triangular solve can begin on these processors while Cholesky is still running elsewhere. This combination of load imbalance and dependency-driven fu-sion hides about 90% of the standalone solve time, allowing the solve to execute nearly for free. In the block-cyclic con-figuration, work is more evenly balanced across processors, leaving less idle time to exploit; fusion therefore hides only 18–23% of the solve, while still outperforming sequential ScaLAPACK Cholesky followed by TRSM by 1 .30–1 .62 ×.

7 Related Work 

Systolic arrays were introduced by Kung and Leiserson [16, 17]. Rajopadhye, Fujimoto, and Purushothaman [29–31], as well as Quinton [26, 27] established how to synthesize them from uniform and affine recurrence equations. There is a long history of dataflow compilers based on the polyhedral and affine models. AutoSA [37] and PolySA [9] use the polyhedral model to find unit-length read distances among loop nests and then compile the equations to dataflow. They primarily target matrix multiply and convolution, and do not handle recurrences (equations with dependencies) beyond the LU decomposition, whose dataflow resembles matrix multiply. Lam did early work on systolic-array compilation, while Lam and Wolfe studied locality optimization [21, 22]. AlphaZ [39–41] is the closest equational system, instan-tiating recurrence equations on distributed-memory ma-chines. Users explicitly provide space–time maps, including statement-ordering dimensions that Cyclotron instead infers. Its distributed backend emits nearest-neighbor systolic halo exchanges using blocking MPI_Send and MPI_Recv , whereas Cyclotron expresses broadcasts, relays, and piecewise rings directly in the recurrence system. Legion [3] also derives communication from programmer-declared data dependen-cies, but does so dynamically at runtime rather than stati-cally. Its programs also explicitly order per-timestep kernel launches, whereas Cyclotron derives this ordering from the space–time mapping. Thus, Cyclotron’s ordering algorithm is complementary to Legion and could sit above it. Our IR is an extension and re-imagining of the assignment-free notation from the Algorithms of Informatics textbook by Gyires [13]. Their notation is array-style, similar to Halide’s input language [28] (e.g. 𝐴 (𝑖, 𝑗, 𝑘 ), as opposed to our (𝑖 𝑗𝑘 )𝐴 ). Halide’s notation is adapted by the Stellar [12] and Gem-mini [11] work for designing matrix-multiply systolic arrays. Cyclotron extends this style of notation to express multiple communication patterns, combinations of them, and gimbal-locked indexing. Calyx [24] and Dahlia [23] provide IRs for synthesizing accelerators with explicit control and mem-ory pipelines, but do not reason about affine recurrences or induce space–time schedules. The Wavefront Array Proces-sor [18] was a programmable systolic array whose language resembled the per-PE programs Cyclotron generates. DISTAL [38] is a tensor-algebra compiler, built on TACO [15], that generates distributed matrix-multiplication kernels. DIS-TAL separates tensor distribution from computation sched-uling, with communication inferred from these choices; it supports only output-stationary programs without output de-pendencies. Matrix-multiply algorithms include Cannon [6], SUMMA [35], and PUMMA [8], COSMA [20], Johnson [1], and Solomonik [32]. Early work by [14] explored distributed triangular solve, and [19] and [2] investigated communication-optimal Cholesky. The distributed linear-algebra libraries ScaLAPACK [7], SLATE [10], Elemental [25] and DPLASMA [4, 5] implement variants of matrix multiply and solvers. 

8 Conclusion 

We present Cyclotron, a language and compiler that makes communication an expressible, first-class part of distributed tiled algorithms. By separating communication from compu-tation and space–time mapping, Cyclotron lets programmers change how data moves without rewriting the computa-tion itself, and makes it practical to explore a broad space of communication schedules. Across CPUs and GPUs, this Anonymous 

flexibility allows Cyclotron to match and often outperform hand-optimized distributed linear algebra libraries, while showing that the best schedule depends on the machine, algorithm, and problem size. This work opens the door to deeper exploration of communication strategies for general networks of interacting processing elements, from multi-die GPU systems to wafer-scale engines and spatial dataflow accelerators. We believe this can enable software to better express and adapt to increasingly heterogeneous commu-nication patterns as the hierarchies and interconnects of distributed computing platforms continue to diversify.
