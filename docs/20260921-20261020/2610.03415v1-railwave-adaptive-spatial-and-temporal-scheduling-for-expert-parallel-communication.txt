## ABSTRACT 

Irregular All-to-All communication is a major bottleneck in expert-parallel Mixture-of-Experts (MoE) models. Even with fixed expert routing and placement, uneven utilization of parallel network Rails and incast can limit communication performance. We present RailWave, a phase-adaptive communication layer built on DeepEP that addresses these bottlenecks below the routing layer through spa-tial and temporal traffic shaping. RailBalance redistributes source traffic across eligible Rails using source-local information, while a reusable, topology-derived permutation schedule limits concurrent senders per receiver without rebuilding demand-dependent schedules for each communication phase. A lightweight calibrated selector chooses an execution path according to each phase’s traf-fic characteristics and offline profiling results. On training-derived communi-cation workloads from the 106B GLM-4.5-Air model, RailWave delivers up to 

5.84 × speedup on H800 and 4.36 × on H20 over Native. Code is available at 

https://github.com/CyberSecurityErial/RailWave-EP .

## 1 INTRODUCTION 

Mixture-of-Experts (MoE) models increase model capacity while activating only a subset of param-eters for each token (Shazeer et al., 2017; Lepikhin et al., 2021; Fedus et al., 2022). Expert par-allelism (EP) distributes experts across GPUs, requiring dispatch and combine exchanges between tokens and their selected experts. Because routing induces uneven and input-dependent traffic, these exchanges form irregular All-to-All communication and can become a major bottleneck in MoE execution (Liao et al., 2025; Li et al., 2023). Existing approaches improve MoE efficiency through routing, expert placement, and replication (Lewis et al., 2021; Zhou et al., 2022; Nie et al., 2023; He et al., 2022). Replication-based meth-ods can additionally incur per-layer memory overhead from redundant expert states (DeepSeek-AI, 2025). These mechanisms shape the logical communication demand, but do not fully determine its physical execution. This distinction is particularly important in Rail-optimized clusters, where a high-bandwidth intra-node fabric connects multiple scale-out paths (NVIDIA, 2023; Wang et al., 2024). Even with an optimized dispatch–combine backend such as DeepEP (Zhao et al., 2025), traffic can still be redistributed across eligible Rails and node-pair transfers can overlap in different orders. These execution choices expose two bottlenecks, as shown in Figure 1: (a) Balanced expert and destination-node loads can coexist with concentrated source-Rail traffic, leaving parallel paths un-derutilized. (b) Conversely, balanced source Rails do not prevent multiple senders from converging on the same receiver and creating incast. Our analysis of 900 training step–layer pairs further shows that expert-load imbalance has limited linear explanatory power for Rail imbalance. We therefore jointly control where traffic enters the scale-out network and which node-pair transfers overlap.

MoE communication has been optimized at several layers of the software stack. Upper-layer meth-ods change the demand presented to communication: EPLB, UltraEP, MoonEP, and TAOT ad-just expert placement, replication, or token-to-replica assignment to balance expert or device loads (DeepSeek-AI, 2025; Wei et al., 2026; Chen et al., 2026; Zhang et al., 2026). NetMoE adjusts input-sample placement to exploit network locality (Liu et al., 2025), while node-limited routing restricts the destinations selected for each token (DeepSeek-AI, 2024). These decisions shape the logical demand matrix D. RailWave operates after them and optimizes how the resulting communication is executed. EP communication libraries optimize the dispatch–combine data path across intra- and inter-node fabrics. DeepEP and NCCL-EP use high-bandwidth intra-node communication to stage or redis-tribute tokens before scale-out transmission (Zhao et al., 2025; Goldman et al., 2026). SwiftEP reduces data-path overhead through buffer fusion and TMA offloading (Li et al., 2026), while UBEP combines finer-grained execution with topology-aware scheduling for high-bandwidth su-perpods (Liu et al., 2026). EPIC spans logical and physical optimization, coupling expert migration with topology-adaptive transport and communication–computation overlap (Cao et al., 2026). Rail-Wave builds on DeepEP to control the Rail distribution and concurrent execution of the transfers carried by this backend. Network-aware mechanisms are the closest to RailWave. RailS and FuseLink primarily improve path utilization through local traffic redistribution (Xu et al., 2026; Ren et al., 2025), whereas Rail-Wave additionally controls which node-pair transfers overlap at a receiver. FAST explicitly balances traffic across the GPUs and NICs within each node, then uses demand-dependent Birkhoff schedul-ing to construct balanced one-to-one stages (Lei et al., 2026; Wu et al., 2026). This planning requires a consistent view of source–destination demand across nodes; synchronizing that information and rebuilding schedules can incur substantial overhead as routing changes. RailWave instead reuses topology-derived cyclic peer plans with source-local RailBalance, reducing this coordination and plan-construction overhead. Rate-based scheduling controls incast through sender pacing (Cohen et al., 2026). SABRE selects communication strategies according to endpoint-volume skew (Wei & Bhatele, 2026), whereas RailWave indexes offline-calibrated path decisions by payload, global source-Rail skew, and receiver concentration. Other approaches reduce payload size or overlap communication with computation (Nie et al., 2024; Jiang et al., 2024; Zhang et al., 2025). Permutation scheduling bounds incast degree using cyclic pairwise exchange (Thakur et al., 2005). With N nodes, wave k ∈ { 1, . . . , N − 1} uses 

πk (s) = ( s + k) mod N, π−1 

> k

(d) = ( d − k) mod N. (10) 

Each node has at most one outgoing and one incoming peer in a wave. Every remote ordered pair appears exactly once because its shift is uniquely determined by (d − s) mod N . These peer relationships depend only on group membership and are constructed once; each phase supplies new transfer records and counts. For a wave, the executor selects records whose destination is πk(s) and packs their payload without padding the node-pair demand. This partition operates over backend transfer records, including multiple destinations for the same token. Within each backend invocation, DeepEP and Rail-only admit the submitted remote pairs together, whereas Permutation-only and Joint execute the cached peer plans in order. Within each wave, disjoint node pairs communicate concurrently. Joint applies RailBalance to the records in the current wave. A phase can be balanced across Rails in aggregate while a particular destination slice remains concentrated on a few Rails. Redistributing that slice can shorten the wave’s critical transfer. The gain depends on its Rail skew and relocation cost; scheduling still serializes the waves and retains the original differences in node-pair demand. 3.3 CALIBRATED EXECUTION SELECTION 

No single execution path dominates across communication phases. RailBalance is beneficial when improved Rail utilization outweighs local redistribution, while permutation scheduling is beneficial when reduced incast outweighs the cost of additional communication rounds. These break-even points vary with traffic characteristics, motivating phase-specific execution selection. The selector uses three traffic descriptors defined in Section 2.2: the average remote payload per GPU B, the global source-Rail skew ρg , and the receiver concentration κ under the actual sending windows. Together, they capture communication scale, source-Rail imbalance, and receiver concen-tration for the current phase. After fixed normalization calibrated offline, these statistics form the lookup feature x = ( eB, eρg , eκ). Phases with no remote payload retain the Native local path. 6Preprint. ## 4 EXPERIMENTS 

We evaluate RailWave against Native, NCCL, and the released FAST implementation (Lei et al., 2026), isolate the effects of spatial and temporal shaping, and evaluate adaptive execution. Ad-ditional results on integration with an upper-layer expert-parallel system are provided in Ap-pendix A.2. 4.1 EXPERIMENTAL SETUP 

Platforms. We evaluate on two 32-GPU clusters equipped with NVIDIA H800 and H20 GPUs, respectively. Each cluster has four nodes with eight GPUs per node. All compared methods use the same communication configuration within each cluster. Detailed hardware and software settings are provided in Appendix A.1. 

Workloads. Our replay is based on expert-routing statistics collected during actual GLM-4.5-Air (GLM-4.5 Team, 2025) training runs on DAPO-Math-17k (Yu et al., 2025), covering all 45 MoE layers. To model incast under variable rank progress, we construct three controlled sending patterns—Ring, Moderate, and Extreme—as detailed in Appendix A.6. 

Baselines and metrics. We compare four execution paths on the same DeepEP backend: N ATIVE ,RAIL -ONLY , P ERMUTATION -ONLY , and J OINT . Native and Rail-only retain the replayed transfer order, whereas Permutation-only and Joint use cyclic waves; Joint additionally applies RailBalance within each wave. RailWave selects among these paths using the calibrated lookup described in Sec-tion 3.3. We also compare against NCCL all to all single and the released FAST implemen-tation. The plotted latency is the GPU-event communication interval: all waves of dispatch–combine for the DeepEP paths, or the corresponding forward–return All-to-All for NCCL and FAST, includ-ing RailBalance GPU operations when enabled. CPU planning, index construction, and prepacking are outside this interval for every method, as detailed in Appendix A.6. Each plotted P50/P95/P99 is the sum of the corresponding per-layer quantiles over the 45-layer replay. 4.2 OVERALL PERFORMANCE

## 5 CONCLUSION 

We presented RailWave, a communication layer for expert-parallel MoE execution that targets physical-network inefficiencies remaining after expert routing and placement are fixed. RailWave combines source-local RailBalance with reusable permutation scheduling to jointly improve paral-lel Rail utilization and control receiver-side concurrency, while preserving expert assignments and logical communication demand. Built on DeepEP, RailWave achieves communication speedups of up to 5.84 × on H800 and 4.36 × on H20, demonstrating the benefits of jointly shaping the spatial and temporal execution of expert-parallel traffic. UltraEP determines expert placement and maps logical expert IDs to physical experts, while RailWave operates below the routing layer and optimizes how the resulting token traffic is executed on the network. Calibration details. The selector uses x = ( eB, eρg , eκ), with

Motivation. Megatron-style training (Shoeybi et al., 2020) commonly follows single-program, multiple-data (SPMD) execution: ranks run the same program on different data or model parti-tions and coordinate through communication and synchronization. This does not require a central controller to track every rank’s fine-grained progress. Compute-time variation, rank skew, and net-work jitter can therefore change communication overlap even when the logical execution order is unchanged. Single-controller runtimes can explicitly coordinate cross-stage tasks (Xhebraj et al., 2024), but centralized coordination is not a defining property of the multiple-program, multiple-data (MPMD) model. We use training-derived layer loads with controlled sending arrangements to cover possible incast conditions, rather than replaying one incidental training timeline.
