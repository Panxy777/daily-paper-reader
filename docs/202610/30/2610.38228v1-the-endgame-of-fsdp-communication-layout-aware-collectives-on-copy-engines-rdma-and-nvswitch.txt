## Abstract 

Fully Sharded Data Parallelism (FSDP2) maintains parameters and gradients as per-parameter tensors, whereas its collective path operates on flat, rank-major buffers. Converting between these layouts copies all-gather outputs into parameter storage and packs gradients into full-group fp32 buffers. Layout conversion alone accounts for 6.4% of step time in Llama-3.1 70B training at 8K tokens per GPU. Communication kernels impose a second cost: a default NCCL reduce-scatter can slow a concurrent GEMM that would otherwise complete in a single wave by 69%. We present TIDE, a set of zero-copy collectives built on public NCCL 2.31+ APIs. TIDE preserves FSDP2’s per-parameter storage and compute kernels while folding layout placement into collective addressing. TIDE-AG delivers shards directly to parameter storage using NVSwitch multicast and paced recursive-doubling RDMA, with no SMs used for transport or placement. TIDE-RS consumes per-parameter bf16 gradients directly and reduces them into fp32 

shards—a mixed-precision mode that NCCL does not provide—using copy engines and short-lived thread blocks (CTAs) for node-local accumulation and NVSwitch for cross-node reduction. A two-phase pipeline separates gradient reads from network progress; Slot-Reuse optionally stages gradients in vacated all-gather slots. On 64 GPUs, TIDE reduces step time by up to 27.1% relative to Stock FSDP2 and 6.0% relative to FSDP2+SymmMem across Llama-3.1 70B, Wan2.2, and Qwen3-30B-A3B. It reduces reduce-scatter SM time by factors of 12 .5–14 .5 and cuts interference with concurrent compute by up to an order of magnitude. Its reduce-scatter buffer remains nearly constant from 16 to 64 GPUs at a fixed per-GPU output size, and its peak memory is up to 4.7 GiB below FSDP2+SymmMem’s and, with Slot-Reuse on Wan2.2, below Stock FSDP2’s.

## 1 Introduction 

Fully Sharded Data Parallelism (FSDP2 [21, 51]), rooted in ZeRO-3 [35], is the workhorse paradigm for training dense and Mixture-of-Experts (MoE) foundation models [9, 20, 34] across hundreds to thousands of GPUs [17, 33]. Wire speed is not end-to-end efficiency. Well-tuned large-message collectives approach link bandwidth on NVSwitch nodes with rail-aligned RoCEv2 or InfiniBand NICs, yet FSDP2 pays for more than wire time. Its model view is per-parameter: 𝑃 independently shaped tensors, each with a persistent dimension-0 DTensor shard [4, 30]. Its collective path is rank-major and flat: NCCL sees contiguous buffers ordered by rank, and our target configurations reduce gradi-ents in fp32 . Translating between the two layouts and sharing SMs and HBM with the model cost three measurable forms of overhead (Figure 1, Section 2): (1) Layout conversion and packing. Stock FSDP2 copies each rank-major all-gather output into per-parameter storage and packs bf16 gradients into a transient full-group fp32 buffer before each reduce-scatter, so each group’s parameters and gradients briefly exist twice, and the copies take 0.33 s of each Llama-3.1 70B step at 8K tokens/GPU. (2) SM wave quantization. Small-𝑀 GEMMs in MoE layers and narrow projections often finish in one wave of thread-block clusters. A reduce-scatter that stays resident for the whole transfer pushes part of that wave into a second one: NCCL’s default reduce-scatter slows such a GEMM by 69%, and its symmetric-memory variant by 11% at the median. (3) HBM direction contention. Per byte served, remote service reads and switch-reduction reads slow co-running memory-bound kernels 2 .2–4 × more than inbound copy-engine writes, depending on the clock regime (Section 2.4). Why existing approaches fall short. Existing systems fix one side of the problem or change FSDP2’s storage contract (Table 1). Py-Torch’s symmetric-memory FSDP2 path [26, 32] removes all-gather transport SMs but keeps rank-major outputs, full-group gradi-ent packing, and 13 reduce-scatter CTAs. AMD MORI [1] lands all-gather data directly within one node; PACE [27] extends di-rect placement to reduce-scatter but stages and converts its multi-tensor input in a 32-CTA SM ring. Megatron-FSDP [23] and veScale-FSDP [45] avoid packing by replacing per-parameter storage with persistent flat windows. Among the systems considered, none con-sumes per-parameter tensors directly across nodes, keeps fp32 re-duction, and moves transport off SMs while leaving FSDP2’s storage intact. 

Our approach and contributions. Layout conversion in FSDP2 is a collective problem, not a copy problem. When the collective itself reads every tensor where the model stores it and delivers every result to its final address—with copy engines, RDMA, and NVSwitch moving the bytes and SMs performing only short-lived 

fp32 accumulation—the layout copies, the packing buffers, and most of the SM interference disappear together. TIDE builds such collectives on public NCCL 2.31+ APIs (Figure 2). They are zero-copy in a precise sense: FSDP2’s layout copies (all-gather copy-in and copy-out, and reduce-scatter packing) and their full-group buffers are gone; only required dtype casts, bounded multi-node staging, and an optional memory-saving gradient copy remain. The design also frees memory: all-gather slots double as parameter storage and, optionally, as reduce-scatter input. This paper makes three contributions: 

• Zero-copy collectives (Sections 2 to 4): TIDE-AG and TIDE-RS consume FSDP2’s per-parameter tensors without packing. TIDE-AG uses no SMs: copy engines multicast shards through NVSwitch, and paced recursive-doubling RDMA carries them across nodes. TIDE-RS reduces bf16 gradients into fp32 shards, a mixed-precision mode that NCCL lacks. Copy engines push slices to their owners, short-lived TMA CTAs sum them into fp32 

node partials, and Latin-square placement lets the destination NVSwitch sum up to 𝐿 nodes’ partials in one reduction. 

• Pipelining, memory, and runtime (Sections 5 and 6): A two-phase pipeline separates gradient reads from network progress. In-Place mode reads gradients where autograd leaves them and runs the next all-gather early; Slot-Reuse mode copies them into a vacated all-gather slot and frees their storage. ## 2.3 Limits of Symmetric Input Windows 

NVSwitch reduces in the switch via PTX multimem.ld_reduce [24], so one might place unsharded gradients in a symmetric window and let each owner reduce the 𝐿 = 8 local copies with a 2-CTA kernel. With per-parameter bf16 gradients and fp32 reduction, this fails either way: (1) A bf16 window breaks fp32 semantics. The acc::f32. bf16x2 form of multimem.ld_reduce accumulates in fp32 but returns bf16x2 , so every node partial is rounded to bf16 before cross-node accumulation, and small contributions can be lost as 𝑀 grows. (2) An fp32 window is prohibitive. multimem.ld_reduce. add.v4.f32 needs fp32 inputs: a persistent 2 𝑁 𝑆 -byte sym-metric allocation per active group (2 × the unsharded bf16 

group), plus either rewriting every gradient-producing kernel to write fp32 into window offsets or an SM cast-pack pass that reintroduces the traffic, SMs, and buffers TIDE removes. TIDE instead consumes FSDP2’s native bf16 gradients, stages bounded chunks, and accumulates once in fp32 locally. 

## 2.4 The HBM Direction Tax 

Even with an fp32 window, traffic direction matters: per byte served, remote service reads disrupt compute 2 .2–4 × more than inbound copy-engine writes, depending on the clock regime. In a 2 ×2 matrix of initiator (SM or copy engine) and direction (pull or push), GPUs 1–7 generate traffic against GPU 0 while it runs a 256 MiB bf16 

memory-bound victim (Table 3). Normalized by served bandwidth, pulls slow the victim by 5.2–5 .9% per 100 GB/s and pushes by 1 .4–1 .7%. The asymmetry is not a power-cap artifact: at a fixed 1200 MHz SM clock, pulls cost 4 .46 (SM) and 3 .81 (copy engine) versus 2 .04 and 1 .21% per 100 GB/s for pushes, a 2 .2–3 .2× per-byte gap. Across the two clock regimes, a pull therefore costs 2 .2–4 × as much per byte as a push, and we quote this range rather than a single factor. A real 2-CTA switch-reduction collective slows the same victim by 27%, TIDE-RS by 2 .6%. L2-resident victims (32–64 MiB) slow by at most 3 .4%, so the cost is HBM contention, not L2 eviction. DRAM counters show no extra bytes, consistent with interleaved service reads lowering DRAM efficiency while inbound writes are coalesced before writeback. 

Architectural synthesis. These findings shape TIDE-RS’s two lev-els (Figure 2b). Within a node, copy engines push unreduced bf16 

gradients 4 —half the bytes, in the low-interference direction—into small staging chunks, and 4–16 TMA CTAs 5 accumulate the 8 → 1 sum in fp32 . Across nodes, each node contributes one 4-byte 

fp32 partial per element instead of eight 2-byte values (4 × less in-put); partials arrive over rail RDMA 6 , and multimem.ld_reduce. add.v4.f32 7 lets 1–4 landing CTAs fold up to 8 nodes per wave in fp32 . Switch reads thus see only the 4 × smaller partial stream. 

## 2.5 Design Requirements and Scope 

TIDE targets six requirements: 

• G1 (Preserve the FSDP2 contract): per-parameter dimension-0 

DTensor shards, fp32 reduction, and unmodified compute ker-nels. 

• G2 (Placement, not packing): land all-gather shards in parameter-major storage and consume per-parameter gradients directly, keeping only required dtype casts. 

• G3 (Bound SM interference): no SMs for all-gather, and a reduce-scatter CTA budget independent of node count, with no peer polling on SMs in the default path. 

• G4 (Scale across nodes): 𝑂 (log 𝑀 ) all-gather rounds, about 

𝑂 (𝑀 /𝑘 ) wave-aligned reduce-scatter rounds with 𝑘 concurrent rail transfers each, and rail communicators over 𝑀 rather than 

𝑁 ranks. 

• G5 (Bounded memory): no persistent full-group fp32 window, a closed-form memory model, and two time–memory modes. 

• G6 (Public NCCL APIs): public NCCL 2.31+ APIs only; unsup-ported groups fall back to stock collectives. TIDE targets PyTorch 2.13, dimension-0 sharding, node-major deployments with up to eight GPUs per NVSwitch domain, rail-aligned RDMA NICs, NVSwitch multimem , and compute capability

## 3 TIDE-AG: Layout-Aware All-Gather

Coalescing the destination-rank axis. Flattening every destina-tion row separately requires (𝐿 − 1)𝑃𝑀𝐿 copy descriptors per rank per call (107 ,520 at (𝐿, 𝑀, 𝑃 ) = (8, 64 , 30 )). Keeping pace with the rail. At 𝐿 = 8, each 4-byte fp32 node partial requires eight bf16 reads (16 bytes) and one fp32 write (4 bytes), so Level 1 must process 5 × the NIC output rate: 237.5 GB/s of logical read-plus-write traffic for a 47.5 GB/s rail. A warp-specialized TMA pipeline raises the kernel-only rate from 32 to 99 GB/s per CTA in this metric; on six nodes, a reduce-scatter takes 4.81 ms with four sum CTAs versus 4.60 ms with eight, so four CTAs keep up with a 400 Gb/s rail. The sum CTAs retire when the read phase completes and never poll peers, so extra CTAs add transient contention with-out reserving SMs for the network transfer; the pipeline can use more of them to meet an earlier gradient-read deadline.

## 5 Pipelining and Memory Efficiency 

Low-SM collectives must still become training-level overlap with bounded memory. TIDE separates gradient reads from network progress and makes gradient residence an explicit choice: In-Place keeps gradients in autograd storage and prefetches the next all-gather early, while Slot-Reuse moves them into a vacated all-gather slot and frees their storage immediately. 

## 5.1 Scheduling and Allocator Constraints 

Let ℓ index layers in forward order and 𝑒 successive reduce-scatter calls. When TIDE-RS reads autograd’s gradients {𝐺 𝑝 } in place, they stay live until its Level 1 pushes and sums finish; FSDP2 keeps a collective’s input until the next group’s post_backward observes its completion event, which is therefore the default release point. Three constraints shape the schedule. 

Read–network coupling. With one shared outbox bank, call 𝑒 

cannot start reading until call 𝑒 − 1’s sends release the bank, and forcing the compute stream to wait for reads puts their latency on the critical path. Local reads therefore need independent temporary state. 

The host-time allocator paradox. Asynchronous reclamation via 

record_stream or a polling thread is GPU-safe, but PyTorch’s caching allocator assigns blocks when the CPU enqueues work, one or two layers ahead of the GPU. By the time an event reports layer ℓ safe to free, later layers have already claimed fresh segments (Figure 13, Appendix E), so reclamation must happen at an allocator-visible host callback. 

Backward prefetch inversion. FSDP2’s post_backward enqueues the current reduce-scatter before the next pre_backward enqueues the next all-gather, which can then wait behind a whole multi-node network phase. Whether TIDE can move it ahead depends on the mode: In-Place leaves the landing slot free, whereas Slot-Reuse stores gradients there until reads complete.

## 6 Implementation and Runtime 

TIDE comprises about 5,100 lines of C++/CUDA, 2,300 lines of Python, and 1,800 lines of tests. It uses only public NCCL 2.31 APIs (symmetric windows, local peer pointers, multicast bindings, and RMA puts and signals), so it runs on unmodified NCCL; all reported runs use stock NCCL 2.31.2. The FSDP2 adapter replaces FSDP2’s internal all-gather, copy-out, reduce-scatter, unsharded-parameter allocation, and post-forward (and, for In-Place, backward-prefetch) hooks after checking their signatures; model code and compute kernels are unchanged. Neither collective copies metadata to the GPU per call: the reduce-scatter passes gradient pointers as kernel parameters and reads a segment table uploaded at registration. The control plane must scale too: TIDE bounds connection state with topology-scoped communicators, host submission with a small stream pool, and SM and memory use with plan selection. 

## 6.1 Topology-Scoped Communicators 

A single symmetric-window RMA communicator scales poorly. In NCCL 2.31’s host RMA proxy, the first ncclCommWindowRegister

𝑛 ctx RMA contexts to every rank and runs an 𝑁 -rank ring barrier after each connection: 𝑂 (𝑛 ctx 𝑁 2) barrier steps and 2 𝑛 ctx 𝑁 QPs per GPU. Yet rank 𝑟 = 𝑛𝐿 + 𝑙 only ever sends to its 𝑀 − 1 same-rail peers, so TIDE splits the domains: (1) Node-local domain. The main 𝑁 -rank communicator has no RMA contexts but keeps local symmetric addressing (LSA) peer pointers and NVSwitch multicast. (2) Rail domains. ncclCommSplit forms 𝐿 disjoint 𝑀 -rank rail communicators with 𝑛 ctx contexts each (four in our evaluation). (3) Shared storage. Each arena is registered in both domains; the main handle serves LSA and multicast, the rail handle RMA. Both communicators cap their unused NCCL channels at one. The split cuts per-GPU QPs by 𝐿 × and barrier work by 𝐿 2× (8 × and 64 × at 𝐿 = 8). On 8 nodes, with lazy connection, communicator state takes 0.21 GiB per GPU versus 6.95 GiB for eager 32-channel initialization, and the rail split plus RMA connection takes 1.3–1.7 s .

## 6.2 Bounded Host Execution 

Long copy-descriptor chains can block host submission behind queued GPU work. TIDE spreads descriptor batches over a small pool of internal streams, with device-side slot counters preserving order, which keeps median enqueue latency at 0.62 ms for TIDE-AG and 0.80–0.82 ms for TIDE-RS across tested queue depths. The network phase is host-driven by default, and in training this host work stays hidden behind backward compute. Where NCCL’s GPU-initiated networking (GIN) runs over GDAKI, an optional device path replaces per-round host calls with a 1-CTA kernel per wave (Appendix G); all reported results use the host path. 

## 6.3 Plan Selection and Validation 

Before the first registration, a calibrated first-order model picks the sum and landing CTA budgets, round width 𝑘 , chunk size, pass count, and outbox depth from measured NIC, local-sum, landing, and per-round wait rates: it provisions enough local-sum through-put to feed the rail, bounds the landing tail, and widens rounds only when that amortizes peer waits (Appendix G). On our eight-node system, the solver selects 𝑘 = 4 and four sum CTAs. Because over-lap tightens the gradient-read deadline, the training configuration raises the sum budget to 16 (Section 7.1), which changes neither placement nor arithmetic. At installation, all ranks agree on tensor signatures, options, and capabilities; unsupported groups fall back to stock collectives, and inconsistent global capabilities abort. A 239-configuration test suite covers bitwise and tuning invariance, non-finite inputs, HSDP and expert subgroups, EMA/checkpoint paths, and 41 fault-injection negative tests over 11 fault kinds (Ap-pendices E and F).

## 7.1 Experimental Setup 

We use up to eight nodes, with eight GPUs per NVSwitch domain and one RDMA rail per GPU; all training runs use 64 GPUs. We train dense Llama-3.1 70B at 8K–32K tokens/GPU, the MoE Qwen3-30B-A3B at 16K–32K tokens/GPU, and the high-noise expert of Wan2.2-T2V-A14B , a 14B dense diffusion transformer, at 17 frames and local batch 1–4 (7.8K–31.2K tokens/GPU). We compare Stock FSDP2, FSDP2 with PyTorch Symmetric Memory (FSDP2+SymmMem), and TIDE, using In-Place for Llama and Qwen3 and Slot-Reuse for Wan; TIDE-RS runs 16 sum and 4 landing CTAs with 𝑘 = 4. All systems share the model, precision, optimizer, activation checkpointing, and inputs. We report median step times over 40–100 post-warm-up steps from repeated launches and pair launches by round; memory is the whole-device peak. 

## 7.2 End-to-End Performance and Memory 

TIDE is the fastest system at every point (Figure 8a–c). On Llama it cuts step time by 16.2% at 8K tokens/GPU and 3.1% at 32K versus Stock, and from 16K to 32K it saves 0.51–0.54 s per step, 1.9–2.4 ×

what FSDP2+SymmMem saves, so the relative reduction shrinks only because the step grows. Wan shows the same pattern on a shorter step: 7.4%, 2.8%, and 1.4% versus Stock at 7.8K, 15.6K, and 31.2K tokens/GPU, about twice what FSDP2+SymmMem saves at the two larger sizes. For Llama and Wan, every paired-𝑡 95% interval against FSDP2+SymmMem excludes zero, and fixed-clock reruns of Llama 24K and Wan at 15.6K tokens/GPU keep the same ordering. Qwen3 shows the largest gains, as Equation (1) predicts: sparse MoE routing activates only a small fraction of the sharded parame-ters per token, while every rank still gathers and reduces the full parameter volume, so the recoverable overhead is a larger share of the step. From 16K to 32K tokens/GPU, TIDE cuts step time by 27.1%, 21.4%, and 17.3% versus Stock and by 6.0%, 4.8%, and 4.3% versus FSDP2+SymmMem (Figure 8c). TIDE uses less memory than FSDP2+SymmMem on all three models, and Slot-Reuse uses less than Stock on Wan (Figure 8d). At Llama 24K, FSDP2+SymmMem holds the same live bytes as Stock but peaks 6.6 GiB higher: its private pool reserves 9.4 GiB that no other tensor can share, more than TIDE’s whole 6.1 GiB arena, which also holds the unsharded parameters. Stock takes the fp32 reduce-scatter input from the compute pool, where it shares memory with activations. In-Place therefore peaks 4.7 GiB below FSDP2+SymmMem, adding 1.9 GiB over Stock, mostly a communicator and an arena reserved once for the largest group (Llama’s vocabulary layer); its reduce-scatter staging does not grow with the GPU count (Section 7.4). On Wan, Slot-Reuse peaks 1.0– 1.4 GiB below Stock and 1.5–1.7 GiB below FSDP2+SymmMem. In-Place is only 0.3% faster at batch 2 and uses 0.8 GiB more, so Wan uses Slot-Reuse. On Qwen3 at 32K tokens/GPU, TIDE peaks 3.7 GiB below FSDP2+SymmMem (87.3 vs. 91.0 GiB), within 0.3 GiB of Stock. 

## 7.3 Where the Gain Comes From 

Both collectives contribute, and the gains add. Replacing one col-lective at a time, in separate In-Place launches, returns about half the combined saving: the all-gather alone is 50% of it at Llama 24K and 55% at Wan 15.6K, the reduce-scatter alone 58% and 43%, and the two shares sum to 108% and 98%. TIDE removes the layout copies and keeps communication off the SMs. In a profile of one GPU during a Llama 8K step, Stock and FSDP2+SymmMem spend 0.33 and 0.32 s per step on those copies. Communication drops from 78 SM ·s per step under Stock and 34 under FSDP2+SymmMem to 3.8, and a communication kernel is resident for 8% of the step instead of 89% and 59%. TIDE’s GEMMs are 1.3% and 5.5% shorter than under the two baselines. TIDE-AG is the fastest all-gather and barely slows concurrent compute; TIDE-RS cuts that slowdown several-fold (Figure 9; Ta-ble 6 lists the values). TIDE-AG uses no SMs, so concurrent compute slows by at most 0.5%. FSDP2+SymmMem cuts all-gather SM time by 2.5–2.7 × but barely touches the reduce-scatter, whose packing and reduction still run on SMs. TIDE-RS uses 12.5–14.5 × less SM time than either baseline, lowering the slowdown from 9.6–11.6% to 3.5% on Llama and from 20.6–23.2% to 2.1% on Wan. The advantage holds beyond the training shapes. Only TIDE’s training configuration finishes a 32 MiB reduce-scatter on 8 nodes faster than Stock FSDP2 while slowing a one-wave GEMM by less than 4% (Appendix A, Table 4, and Figure 11); against a large GEMM and a memory-bound kernel, the training configuration adds 4.2% and 1.6%, versus 13.6% and 13.3% for Stock FSDP2. 

## 7.4 Scaling and Resource Efficiency 

TIDE-AG stays ahead of FSDP2’s fastest all-gather, copy-out in-cluded, and uses no SMs (Figure 10a). Across 1–8 nodes and 32– 128 MiB shards the median speedup is 1 .06–1 .42 ×. On 128 MiB shards it grows from 1 .13 × at 16 GPUs to 1 .42 × at 64; 32 MiB shards stay between 1 .06 × and 1 .22 ×.TIDE-RS keeps a flat buffer while FSDP2’s grows with the GPU count (Figure 10b). FSDP2 packs one fp32 block per GPU, each the size of the output shard, so a fixed output makes that buffer linear in the GPU count. TIDE-RS stays within 18–21 such blocks from two to eight nodes (0.58–0.64 GiB at 32 MiB outputs and 2.26–2.51 GiB at 128 MiB), and FSDP2’s buffer is 3 .2× as large at 64 GPUs for both sizes (0 .9× and 1 .7× at 16 and 32). For a fixed model, FSDP2 packs 2 𝑁 𝑆 at every scale; the 64-node analysis of Section 5.4 bounds TIDE’s staging at 0 .59 𝑁 𝑆 (In-Place) and 0 .16 𝑁 𝑆 

(Slot-Reuse), at most 1.2 and 0.3 GiB per GPU on Llama’s largest group against FSDP2’s 3.9 GiB. On one node TIDE-RS is also 1.4– 1.8 × faster than both FSDP2 paths, and for 128 MiB outputs on eight nodes its median latency is lower than both (Table 8).

## 8 Related Work 

Sharded data parallelism and layout restructuring. ZeRO [35], ZeRO++ [42], MiCS [48], PyTorch FSDP [51], FSDP2 / TorchTi-tan [21], and SimpleFSDP [47] partition model states across data-parallel ranks, while Megatron-LM [18, 38] and DeepSpeed-MoE [34] combine data, tensor, sequence, and expert parallelism. FSDP2’s per-parameter layout forces the packing and copy-out of Section 2.1; veScale-FSDP [45] and Megatron-FSDP [23] remove them by restructuring model storage around persis-tent flat or uneven collective buffers. TIDE instead preserves FSDP2’s per-parameter DTensor storage and expresses non-contiguous placement through a byte table, analogous to MPI derived datatypes [11, 40]. 

Symmetric memory and direct placement. NCCL 2.28–2.31 [24, 26] exposes symmetric windows, copy-engine collectives, NVLink SHARP multimem , host RMA, and device GIN. Related symmetric-memory and direct-placement systems include PyTorch’s FSDP2 in-tegration [32], AMD MORI [1], DeepEP [49], and NCCL PACE [27]. PyTorch’s symmetric FSDP2 path removes all-gather transport SMs but keeps rank-major outputs and gradient packing, and its multi-node copy-engine all-gather is unpaced, which can trigger RoCE incast (Section 3.1). TIDE co-designs placement for both collectives while preserving FSDP2’s storage contract. 

Collective libraries and GPU-initiated communication. NCCL [26] is the de facto GPU collective library, and Hu et al. [14] dissect its protocols and algorithms. Blink [43], TACCL [37], and MSC-CLang [8] generate or express topology-aware collective algorithms, and MSCCL++ [15] exposes GPU-driven communication primitives. Zejian Wang et al. 

GPUDirect Async [2] lets the GPU trigger network operations pre-pared by the CPU, and Unat et al. [41] survey GPU-centric commu-nication more broadly. TIDE adds no programming model: it com-poses NCCL’s public copy-engine, symmetric-memory, multimem ,and RMA primitives into collectives whose output layout matches FSDP2’s storage. 

GPU sharing and interference. Co-running kernels contend for SMs, registers, shared memory, and memory bandwidth. Chimera [29] and Simultaneous Multikernel [46] add hardware preemption and fine-grained sharing of each SM among kernels, while REEF [12], Orion [39], and Tally [50] preempt, schedule, or slice co-located DNN kernels in software to bound interference. For concurrent computation and communication, ConCCL [3] moves all-gather and all-to-all, but not reductions, onto GPU DMA engines, and FiCCO [28] explores DMA-based finer-grain overlap. TIDE shares this goal for FSDP2’s collectives: it keeps transport off SMs, models the remaining SM cost by cluster slots and resi-dence time (Section 2.2), and adds the direction-dependent HBM asymmetry of Section 2.4. 

Overlap and in-network reduction. CoCoNet [16], decomposi-tion pipelines [44], Centauri [7], T3 [31], FLUX [6], TileLink [52], and FlashOverlap [13] fuse or schedule compute–communication overlap across general, tensor-parallel, and MoE workloads. TIDE instead targets the FSDP2 layout boundary while leaving com-pute kernels unchanged. InfiniBand SHARP [10], SwitchML [36], and ATP [19] aggregate inside the inter-node network. TIDE in-stead maps remote partials onto destination GPUs so a node-local NVSwitch performs the final fp32 reduction across multi-node rail topologies, without programmable inter-node switch support. 

## 9 Conclusion 

Layout conversion in FSDP2 is a collective problem, not a copy problem. Solving it inside the collective lets TIDE keep FSDP2’s per-parameter storage, overlap gradient reads with the network through a two-phase pipeline, and reuse all-gather slots as parameter storage and, optionally, as reduce-scatter input. On 64 GPUs training Llama-3.1 70B, Wan2.2, and Qwen3-30B-A3B, TIDE is the fastest system at every measured point, cutting step time by up to 27.1% relative to Stock FSDP2 and 6.0% relative to FSDP2+SymmMem; its peak memory is up to 4.7 GiB below FSDP2+SymmMem’s and, with Slot-Reuse on Wan2.2, below Stock FSDP2’s. Its all-gather uses no SMs and is up to 1 .42 × faster than FSDP2’s fastest all-gather plus copy-out, and in training-shape replays its reduce-scatter cuts interference with concurrent com-pute by 2 .8–11 ×. Throughout, it preserves fp32 reduction and plan-scoped determinism. 

Artifact availability. We intend to release TIDE’s implementa-tion, benchmark drivers, and automated correctness gate upon publication.

## E Pipeline Protocol Details 

Rejected release schedules. Three alternatives motivate the split used in Section 5.2. First, returning read completion while consecu-tive calls shared one outbox bank tied the read event to the previous call’s network phase and lengthened compute-stream waits. Second, forcing the compute stream to wait at a mid-layer release point ex-posed local-read latency on the critical path. Third, record_stream 

and event-polling release preserved GPU safety but occurred too late in host time (Figure 13); peak reserved memory grew because allocations for two later layers had already been enqueued. 

Detailed event protocol. Let 𝐷 rem = 𝑛 part (𝑀 − 1) be the num-ber of remote destination blocks across all passes. Algorithm 1 gives the full schedule; a missing prefetch gate is treated as an already-complete event. Here 𝐽 indexes remote destination blocks, 

outbox [𝑏 ] is bank 𝑏 ’s reusable send storage, and 𝑠 comm is the com-munication stream. Events readyEv , gateEv , and readEv signal source availability, the prefetch gate, and source-read completion; 

sumEv [𝑏 ] [ 𝐽 ] signals local reduction for destination 𝐽 .

Protocol invariants. The implementation checks four invariants with fault-injection negative tests: (I1) every contributor lands ex-actly once and stale blocks from the previous use of the same buffer generation are zeroed; (I2) gradients or slot copies remain live through readEv ; (I3) staging, outbox, and inbox storage is reused only after its previous consumer completes; and (I4) every event or memory-op wait has an earlier producer in the common collective order. 

CUDA hardware work queues. With the default eight CUDA connections, blocking memory operations from the network phase aliased onto the same hardware FIFO as later local reads and stretched the read span; raising CUDA_DEVICE_MAX_CONNECTIONS 

to 32 removed the observed aliasing. This is an empirical require-ment: CUDA does not guarantee each stream its own hardware queue. 

## F FSDP2 Adapter and Expert Subgroups 

Position-aware ring slots and ring-tail folding. Under FSDP2’s default prefetch depth of 1, at most two ring groups are unsharded at once, so group 𝑔 (in execution order) uses all-gather slot 𝑔 mod 2, and TIDE sizes each slot for the groups assigned to it rather than for the global maximum. The final Transformer block ( reshard_ after_forward=False ) is live only across the turn-around bound-ary and alternates with its predecessor like a ring group; TIDE folds it into the 2-slot ring and re-shards it after forward during no-gradient validation, saving a dedicated full-size slot. 

Zero-offset views and PyTorch MemPool accounting. FSDP2 builds unsharded parameters with torch.as_strided at storage_ offset=0 , and EMA validation’s copy.deepcopy of get_model_ state_dict() raises invalid python storage if a DTensor ’s local tensor has a non-zero storage offset. TIDE’s C++ adapter therefore roots a fresh at::Storage at the arena offset, with 

storage_offset() == 0 and its own version counter. To make symmetric arenas visible to torch.cuda.memory_reserved() ,TIDE allocates the arena inside a torch.cuda.MemPool , registers the 2 MiB-aligned pointer with NCCL, and avoids a reference cycle. 

Expert-parallel ( 𝐿 sub = 1) rail lanes and HSDP.. When MoE routed experts are sharded across 𝐸 ep = 𝐿 = 8 modulo subgroups of size 

𝑁 /𝐸 ep , each subgroup has 𝐿 sub = 1 rank per node ( 𝑀 rail peers, no LSA peers), and TIDE specializes both collectives on a dedicated lane. All-gather runs ⌈log 2 𝑀 ⌉ recursive-doubling RDMA rounds directly from landing to landing, with no receive-stage memory or copy-engine scatters. Reduce-scatter skips Level 1 staging, sends 

bf16 pieces across four rail parts into a double-buffered inbox, and uses a fixed eight-source TMA sum to combine the arriving blocks and own contribution in fp32 . Under HSDP, the shard-group output proceeds to FSDP2’s replica all-reduce. 

## G Device-Initiated Path and Sizing Solver 

Device-initiated network phase. When GIN runs over GDAKI, the optional device path runs the network phase as one 1-CTA kernel per wave plus a 1-CTA finalizer on a highest-priority stream. Before launching the kernel for wave 𝑤 , the host queues waits for that wave’s Level 1 sums and, for 𝑤 ≥ 2, for the landing of wave 𝑤 − 2, which last used the same inbox buffer generation. In each round, the kernel waits for per-peer credits, issues striped gin.put calls with a strong signal on the last chunk per peer and RMA context, waits for incoming data signals, and flushes its contexts before an outbox block is reused. Waits are timed against %globaltimer because SM cycle counters stretch under clock throttling. On timeout, the kernel records the NIC send-queue state in mapped host memory and parks in a loop of volatile reads, which the compiler cannot remove as a side-effect-free infinite loop; its completion event therefore never fires, and the host monitor exits fail-stop. 

RoCE traffic-class alignment. GDAKI queue pairs do not inherit the NIC’s global traffic class and otherwise use a lossy priority that can stall under congestion, so TIDE sets NCCL_GIN_IB_TC to the traffic class of the host RMA path before creating communicators.
