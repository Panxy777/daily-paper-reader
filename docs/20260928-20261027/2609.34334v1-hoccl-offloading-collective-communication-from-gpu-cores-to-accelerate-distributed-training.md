## 摘要
大规模语言模型训练涉及在GPU流式多处理器（SM）上进行海量计算，SM是GPU的主要计算单元。由于SM承载了Tensor Core等专用加速器，其高效利用对训练效率至关重要。遗憾的是，现有集合通信系统会与计算争用SM，因为它们会占用SM来执行通信相关的数据移动和同步操作。我们观察到，通信原则上可以由DMA引擎驱动，从而消除SM对通信的参与。基于这一洞察，我们提出HOCCL，一个零SM集合通信框架，由三个组件组成：流管理器、点对点（P2P）执行器和集合调度器。流管理器保持与其他GPU内核的算子级时序顺序。P2P执行器实现零SM点对点通信，而集合调度器编排P2P传输以最大化带宽。实验表明，HOCCL保持接近峰值的通信性能，平均与当前最优水平相差不超过3%，同时使通信不再占用近10%的GPU总SM。通过为计算释放SM资源，HOCCL将端到端训练吞吐量提升最高5%。

## Abstract
Large language model training involves massive computation on GPU streaming multiprocessors (SMs), the primary compute units of GPUs. Since SMs host specialized accelerators such as Tensor Cores, their efficient utilization is critical to training efficiency. Unfortunately, existing collective communication systems compete with computation for SMs, as they consume SMs for communication-related data movement and synchronization operations.   We observe that communication can, in principle, be driven by DMA engines, thereby eliminating SM involvement in communication. Based on this insight, we propose HOCCL, a zero-SM collective communication framework consisting of three components: a stream manager, a point-to-point (P2P) executor, and a collective scheduler. The stream manager preserves operator-level temporal ordering with other GPU kernels. The P2P executor enables zero-SM point-to-point communication, while the collective scheduler orchestrates P2P transfers to maximize bandwidth. Experiments show that HOCCL preserves near-peak communication performance, achieving within 3% of the state of the art on average, while eliminating communication occupancy on nearly 10% of total GPU SMs. By freeing SM resources for computation, HOCCL improves end-to-end training throughput by up to 5%.

## 1. 核心问题与整体含义（研究动机与背景）

- **研究背景**：大语言模型（LLM）训练的海量计算主要运行在 GPU 的流式多处理器（SM）上，SM 集成了 Tensor Core 等专用加速器，其利用率直接决定训练效率。
- **核心问题**：现有集合通信系统（以 NCCL 为代表）需要**占用 SM** 来完成通信数据移动（用户缓冲区 → RDMA 暂存区）与同步操作，从而与计算内核争抢 SM 资源。
- **量化证据**：作者在 32 张 H800（每卡 132 SM）上训练 GPT-6.7B 与 DeepSeek-V2-Lite，用 PyTorch Profiler 测得：
  - TP/EP 虽峰值占用高（16/32 SM），但几乎不与计算重叠，争用率为 0；
  - PP 与 DP 专为与计算重叠而设计，GPT-6.7B 训练中二者平均合计占用 **11.2 个 SM（约 10% 总算力）**；
  - 论文定义**争用率** $I_x=\frac{\int_T C(t)SM_x(t)dt}{N_{SM}\int_T C(t)dt}$，实测总争用率超过 10%，导致前向/后向计算分别变慢约 8.5%/7.7%。
- **整体含义**：论文指出一个被忽视的优化维度——通信设计不应只追求独立带宽，还应**避免侵占 GPU 计算资源**。为此提出将通信从 SM 卸载到 DMA 引擎的零 SM 集合通信框架 HOCCL。
- **为什么不用 VCCL 式方案**：VCCL 通过运行时注册用户缓冲区让 RNIC 直读，但与 PyTorch expandable segments 等 VMM 机制不兼容（碎片开销 >10%），且张量动态分配导致反复注册（毫秒级、峰值数十毫秒），实测可致端到端训练慢近 10%。
- **三大技术挑战**：
  1. **CPU–GPU 协调**：DMA 由 CPU 驱动，但执行状态主要在 GPU 侧，CPU 无法直接观测；
  2. **传输延迟**：DMA 启动延迟约为 SM 拷贝的 5 倍，直接使用会造成 >20% 通信性能损失；
  3. **通信调度**：DMA 引擎是固定功能硬件、不能并行处理多任务，多流需串行共享，调度不当会死锁、带宽失衡或长尾。

## 2. 方法论

### 2.1 核心思想
用 GPU 上原本轻载的 **DMA 引擎（copy engine）** 替代 SM 完成通信数据搬运，配合 CPU 侧控制面与拓扑感知调度，在**不牺牲通信带宽**的前提下实现"零 SM"集合通信。

### 2.2 系统组成（三大组件）

**（1）流管理器（Stream Manager）——控制面基础**
- 传统通信以 SM 内核形式入队 GPU stream，天然继承 stream 顺序语义；HOCCL 移除该内核后需显式恢复时序。
- 利用 GPU 内存操作硬件（`cuStreamWriteValue32` / `cuStreamWaitValue32`）在**不占用 SM** 的情况下读写 CPU 内存。
- 实现 **CPU–GPU 握手同步协议**：每条 stream 维护 `start_flag` 与 `finish_flag` 两个标志，构成"启动路径 + 完成路径"的显式双向确认，保证通信与前后依赖内核的正确顺序，且标志可安全复用。
- **标志池 + 缓冲区状态机**：每个 staging chunk 关联一个标志，处于 `idle → DMA copying → RNIC processing` 三态，统一协调 RNIC、CPU proxy 与 DMA 引擎的异步进度。

**（2）零 SM 点对点执行器（P2P Executor）**
- **跨节点路径**：
  - **对称 GPU 缓冲区**：在同一 PCIe switch 下选取与 RNIC 等距的"对称 GPU"分配收发两个 RDMA staging buffer，避免额外路径开销；
  - **DMA–RNIC chunk 流水线**：staging 区组织为缓冲池，DMA 填充与 RNIC 发送/接收重叠，摊薄 DMA 启动开销；
  - **多 QP 并行**：每条连接使用多个 RDMA 队列对（如 2/4 个）条带化 chunk，加深流水线以隐藏 CPU–GPU 控制延迟。
- **节点内路径**：
  - **运行时 IPC-handle 交换**：基于 POSIX 信号量 + 共享内存，接收端导出 `cudaIpcMemHandle`，发送端运行时打开并解析目的地址，直接 DMA 写入；
  - **CPU 跨进程同步**：DMA 写完成后由发送端 proxy 投递完成信号量，接收端 proxy 等待后通知对应 GPU stream。

**（3）集合调度器（Collective Scheduler）——两级调度**
- **流量矩阵抽象**：将用户集合操作表示为源流量矩阵 $C$（逻辑流 $f_1..f_{12}$），再扩展为 HOCCL 流量矩阵 $T$，把每条跨节点流 $f_m$ 拆为三段：
  $$f_m \Rightarrow f'_m + f_m + f''_m$$
  即发送端 NVLink 转发拷贝、RDMA 传输、接收端 NVLink 转发拷贝；矩阵元素按式 $T[u,v]=C[u,v]+A_u+B_v$（当 $v=\bar u$）累加转发流量。
- **拓扑感知流调度**：把 $T$ 分解为若干阶段矩阵 $T^1..T^n$，需满足三约束：
  1. **完整性**：$\sum_s T^s = T$；
  2. **每阶段度约束**：每个 GPU 每阶段至多一条出向、一条入向 RDMA 流，避免单卡/单 NIC 成为瓶颈；
  3. **跨域平衡**：以最慢通信域近似阶段耗时 $\tau^s=\max_d L^s_d/B_d$，最小化 $\sum_s \tau^s$。
- **Birkhoff 类分解算法（Algorithm 1）**：先预分解各 NVLink 域内原生流量为匹配分量；循环从残差矩阵中抽取无竞争的 RDMA 匹配、移除最大可行部分、补上转发拷贝、用剩余 NVLink 空闲带宽填充本地匹配，直至调度完毕。
- **流大小感知的 chunk 调度**：单个 DMA 引擎可能同时服务发送转发、接收转发与本地传输；按流字节量比例对固定大小 chunk 做加权交错，使大流获得更多服务、小流被定期照顾，避免长尾。

### 2.3 实现
- 基于 NCCL 代码库扩展，核心运行时 **>3K 行 C++**；另实现 **约 1K 行 C++** 的 PyTorch 兼容后端，接口对齐 `torch.distributed`，切换 NCCL/HOCCL 仅需改环境变量。

## 3. 实验设计

- **测试床**：H800 集群，每节点 8×H800 80GB，节点内 NVLink 单向最高 400 GB/s；每节点 8×Mellanox ConnectX-5 NIC（各 50 GB/s），GPU–NIC 一对一映射；软件栈 CUDA 12.2、驱动 535.161.08、ConnectX-5 固件 28.38.1902、NCCL 2.29.7。
- **对比基线**：
  - **NCCL**（生产级 SM 驱动基线），并额外限制通信内核 SM 预算为 **1/2/4/8 SM**，以显式呈现"带宽–SM 权衡"；
  - **NCCL-CE**（NCCL 2.28 的 copy-engine 模式，仅节点内有效）；
  - **VCCL**（最相关的 host-driven 基线），仅用于端到端对比，理由：标准微基准反复复用同一缓冲会摊薄注册开销、高估 VCCL 收益。
- **通信微基准**（nccl-tests，消息 2 MB–1 GB，报告算法带宽）：
  - 点对点：节点内 P2P、跨节点 P2P；
  - 集合操作：AllGather、All-to-All，各含 Config 1（节点内）与 Config 2（跨节点，16 GPU，每节点取 1 卡以强制走 RDMA 路径）。
- **CPU 开销**：测量节点内/跨节点 P2P 的 CPU launch 时间。
