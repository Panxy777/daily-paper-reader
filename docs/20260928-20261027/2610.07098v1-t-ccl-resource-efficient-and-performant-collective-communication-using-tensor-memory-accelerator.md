## 摘要
基于 Transformer 的大型模型日益依赖多 GPU 执行，这要求 GPU 之间进行频繁的集合通信。现有通信库通常依赖大量 GPU 线程来实现高带宽或低延迟，导致流式多处理器（SM）侧的资源占用很大。这种占用会限制可供其他 GPU 工作使用的资源，尤其是在通信与计算并发执行时。因此，高效的集合通信不仅应实现高集合性能，还应降低其在 SM 侧的资源使用。本文提出 T-CCL，一个面向节点内通信、基于张量内存加速器（TMA）的资源高效集合通信库。T-CCL 将数据移动和归约操作均卸载到 TMA，并将每个集合操作作为一系列流水线化的异步 TMA 操作来执行，在保持高带宽的同时减少集合通信所需的 SM 资源。在 AllReduce、AllGather 和 ReduceScatter 集合操作上的评估表明，在通信资源不受限时，T-CCL 相比 NCCL 最高可提升 2.4 倍；在受限资源预算下最高可提升 3.42 倍；与 NCCL 近期对称内存内核相比仍具竞争力；在剖析案例中占用的 SM 数量相同或更少。在 GEMM 与集合通信重叠的案例研究中，将通信后端从 NCCL 切换为 T-CCL 后，在两块 GPU 上相对于串行基线的平均算子级加速比从 1.12 倍提高到 1.25 倍，在四块 GPU 上从 1.04 倍提高到 1.14 倍，因为 T-CCL 使用更少的 SM 进行通信，从而为重叠的 GEMM 留出更多 SM。作为通信后端集成到 vLLM 后，T-CCL 相比 vLLM 的自动后端调度将端到端推理吞吐量最高提升 1.31 倍，并在对话和偏解码型工作负载的所有评估批次大小上均优于后者。

## Abstract
Large transformer-based models increasingly depend on multi-GPU execution, which requires frequent collective communication among GPUs. Existing communication libraries often rely on many GPU threads to achieve high bandwidth or low latency, resulting in a large streaming multiprocessor (SM)-side resource footprint. This footprint can limit the resources available to other GPU work, particularly when communication and computation execute concurrently. Thus, efficient collective communication should not only achieve high collective performance but also reduce its SM-side resource usage. This paper presents T-CCL, a resource-efficient collective communication library based on the Tensor Memory Accelerator (TMA) for intra-node communication. T-CCL offloads both data movement and reduction operations to TMA and executes each collective as a pipelined series of asynchronous TMA operations, reducing the SM resources required for collective communication while maintaining high bandwidth. Evaluated across AllReduce, AllGather, and ReduceScatter collectives, T-CCL outperforms NCCL by up to 2.4x with unrestricted communication resources and up to 3.42x under restricted resource budgets, remains competitive with NCCL's recent symmetric-memory kernels, and occupies the same or fewer SMs in profiled cases. In a GEMM-collective overlap case study, switching the communication backend from NCCL to T-CCL raises the average operator-level speedup over a sequential baseline from 1.12x to 1.25x on two GPUs and from 1.04x to 1.14x on four GPUs, as T-CCL uses fewer SMs for communication, leaving more SMs available to the overlapped GEMM. Integrated into vLLM as a communication backend, T-CCL improves end-to-end inference throughput over vLLM's automatic backend dispatch by up to 1.31x, outperforming it at every evaluated batch size on both the conversation and decode-heavy workloads.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：Transformer 类大模型的参数、激活与中间张量常超出单卡容量，训练与推理普遍采用多 GPU 执行；张量并行把单层权重与计算切分到各卡，每卡算出部分结果后必须通过 AllReduce、ReduceScatter、AllGather 等集合通信合并或重分布。这些集合在 transformer block 内被反复调用，位于关键执行路径上。
- **核心痛点**：现有集合通信库（以 NCCL 为代表）主要靠**大量 GPU 线程**驱动地址生成与数据搬运来换取高带宽/低延迟，因而在 SM 侧留下很大的资源足迹（线程、CTA、共享内存）。当通信与计算并发（如 GEMM 与集合重叠）时，通信会挤占计算可用资源，反而削弱重叠收益。
- **关键观察**：
  1. 自 Hopper 起，TMA 支持由单个被选线程发起、异步完成的批量多维张量搬运（HBM↔SMEM，含 peer GPU 内存），可用更少线程/CTA 维持高带宽；
  2. 集合通信中**归约本身**是资源消耗大户，而 TMA 还支持异步 element-wise 原子归约（add/min/max），可把归约也从线程卸载出去。
- **整体含义**：高效的集合通信不应只追求高带宽，还应同时压低 SM 侧资源占用，从而在资源受限、通算重叠场景下获得更优的"带宽–资源"权衡。论文据此提出节点内、基于 TMA 的 T-CCL。
- **与已有工作的差异**：NCCL 2.27+ 的对称内存内核虽已引入 TMA，但仅用于 load/store 路径、归约仍由大量线程完成、不流水线、且单 CTA 处理多 peer；对称 NCCL 还要求用 CUDA VMM 分配通信缓冲区，难以直接配合 PyTorch 等框架管理的张量。ResCCL 靠调度与灵活 CTA 分配降资源，VCCL 把无归约的点对点搬到 CPU/拷贝引擎，T3、ParallelKittens 走硬件或互连协同设计；T-CCL 则只用 GPU 内已有的 TMA 单元，无需额外硬件。

## 2. 方法论

### 2.1 核心思想
- 将节点内集合通信的**数据搬运与归约全部卸载给 TMA**，并把一次集合组织为**流水线化的异步 TMA 操作序列**，用少量 CTA/线程达成高带宽，从而释放 SM 资源给并发计算。

### 2.2 编程模型
- 参与 GPU 组成 Group，每卡一个 rank；支持单进程与多进程两种模式（多进程复用 ThunderKittens 的 IPC 工具做进程同步与 peer 缓冲区信息交换）。
- 集合接口沿用 NCCL 语义，用户只传本地 buffer，T-CCL 内部解析其他 rank 的对应缓冲区，便于替换 NCCL 后端。
- 同时支持 in-place 与 out-of-place，**优先 in-place**：减少传输任务数，且多进程模式下无需为独立输出缓冲区交换信息。

### 2.3 任务式集合规划
- **分片所有权（shard ownership）**：P 个 rank 把逻辑张量切成 P 个 shard，每个 shard 有唯一 owner 负责产出最终值并向外传播。
  - *shard-in 阶段*：owner 主动从其他 GPU 拉取该 shard 的贡献并在本地归约（利用 P2P 访问，无需对端主动参与）；
  - *shard-out 阶段*：owner 把最终值传播给其余 rank。
- **设计取舍**：优先归约进 owner 本地 shard，而非直接归约进 peer 内存——跨设备归约更贵且需要更严格的原子性保证；由此同步只需发生在集合的**首尾边界**，同步点数量不随消息大小增长。
- **逻辑任务层**：由单一 rank（通常是最低 rank）上的 planner 生成逻辑 copy/reduce/sync 任务，每个任务记录操作类型、执行 rank、源/目的区域与依赖，经预分配缓冲区广播给各 rank。
- **物理任务层**：各 rank 独立把逻辑任务 lower 成物理传输任务（解析地址、选择传输机制），实现"拓扑级优化"与"设备执行级优化"的解耦；本文评测均为对称拓扑与统一 CTA 预算，故 planner 采用对每个 rank 生成相同任务集的简单实现。

### 2.4 TMA 传输引擎
- **Chunk/Window 分解**：物理任务由若干 window 组成，window 再切成固定大小的 chunk（TMA 每步处理的基本单元）；window 用作进度跟踪粒度，window 级完成信号留作未来工作。
- **三项关键优化**：
  1. **Fan-out**：合并"同一源区域、不同目的 peer"的传播任务，本地 shard 的 chunk 只 load 一次进 SMEM，再对 3 个 peer 各做一次 store（3 load → 1 load，store 数不变）；
  2. **按 peer 分 CTA**：把来自不同 peer 的 load+reduce 分配到不同 CTA，避免单一链路的争用或最慢 peer 拖累整体、导致 TMA 硬件闲置；
  3. **小传输单 CTA**：当传输量能装进单 CTA 可用的共享内存时，整个传输交给一个 CTA，避免把少量工作摊到多 CTA 带来的调度与协调开销。
- **流水线 copy/reduction**：在 SMEM 中开 D 级 staging buffer，每级 C 个 chunk，总大小 D×C（须放得进 CTA 可用 SMEM；H100 每 SM 228 KB、单 TB 最多可寻址 227 KB）。逻辑上 **D/2 级用于在途 load、D/2 级用于在途 store/reduce**，原因在于完成机制不同：load 用 barrier 可精确等待某一次，而 store/reduce 通过 commit 组织为 FIFO 异步组，等待某组完成意味着此前所有组都已完成，无法任意单独等待。
  - 流程：先填 D/2 个 load 启动流水线；随后逐级"等待前一个 load 完成 → 发出对应 store/reduce"；在把新 load 发到超前 D/2 的级之前，先等待该级此前的 store/reduce 完成；全部 chunk 发出后 drain 剩余在途操作。论文用 6 chunk、4 stage 的示例说明了 fill / steady-state / drain 三阶段。
- **启动配置调优**：单纯增加 CTA 不一定更快，需要 CTA 数与每 CTA 工作量的平衡。采用**离线扫描**：对每种集合在多种消息大小下评估不同 CTA 配置，按执行时间排序存入以"集合操作 + 消息大小"为索引的查找表；运行时选最近消息大小条目中、能在可用 CTA 预算内满足的最高排名配置。
- **默认参数**：chunk 8 KB、流水线深度 16（staging buffer 共 128 KB）、window:chunk = 1（因尚未使用阶段间信号）。
