## 摘要
分布式推理依赖于 GPU 集合通信，而后者必须跟上不断演进的硬件和专用工作负载。然而，现有集合通信实现通常将语义、编排（数据在何处、何时移动）和数据通路（数据如何移动）耦合在一起。这种耦合使得采用新的硬件机制以及为应用定制通信的代价很高。我们提出 Purlin，一个将这些关注点分离的 scale-up 通信框架。在 Purlin 顶层，我们将集合通信指定为对输入和输出布局的命名，以及一个复制或归约操作。在中间层，我们引入一种共享编排协议 SNAC（Stage, Notify, And Consume），它从这些规格中推导出协调方式。SNAC 之下是称为 Atom 的硬件专用数据通路，它实现了集合通信的两个关键数据移动原语：复制和归约。这种分离使我们能够定制集合通信并采用新的硬件机制，同时通过 SNAC 复用编排。我们在 A100、H200 和 B200 GPU 上评估 Purlin。在七种集合通信操作上，Purlin 相比基线实现了最高 5.14 倍的延迟加速和最高 4.50 倍的带宽提升。集成到 SGLang 后，Purlin 将离线 LLM 服务的吞吐量和交互性相比基线平均提升 1.13 倍，最高提升 1.37 倍。对于在线 LLM 推理，Purlin 将交互性平均提升 1.26 倍，最高提升 2.85 倍，最大增益出现在过载情况下。对于扩散图像生成，Purlin 将端到端延迟最多降低 1.13 倍。

## Abstract
Distributed inference depends on GPU collective communication that must keep pace with evolving hardware and specialized workloads. However, existing collective implementations often couple semantics, orchestration (where and when data moves), and the datapath (how data moves). This coupling makes it costly to adopt new hardware mechanisms and customize communication for applications. We present Purlin, a scale-up communication framework that separates these concerns. At the top of Purlin, we specify collectives as a naming of an input and output layout and a copy or reduction operation. In the middle, we introduce a shared orchestration protocol, Stage, Notify, And Consume (SNAC), which derives coordination from these specifications. Below SNAC sits a hardware-specific datapath we call Atom, which implements two key data movement primitives for collectives: copy and reduce. This separation lets us customize collectives and adopt new hardware mechanisms while reusing orchestration via SNAC. We evaluate Purlin on A100, H200, and B200 GPUs. Across seven collectives, Purlin achieves latency speedups of up to 5.14x and bandwidth improvements of up to 4.50x over baselines. Integrated into SGLang, Purlin improves offline LLM serving throughput and interactivity by 1.13x on average and up to 1.37x over baselines. For online LLM inference, Purlin improves interactivity by 1.26x on average and up to 2.85x, with the largest gain occurring under overload. For diffusion image generation, Purlin reduces end-to-end latency by up to 1.13x.

# Purlin 论文深度总结

## 1. 核心问题与研究动机

- **背景**：LLM 推理依赖张量并行、专家并行、序列并行等分片策略，其间通过 AllReduce、AllGather(V)、ReduceScatter(V)、AllToAll(V) 等集合通信交换中间结果。scale-up 域（NVLink）已从 8 卡服务器扩展到 72 卡机架，并计划延伸至 576 卡。
- **核心痛点**：现有集合通信实现（NCCL、NVSHMEM、MSCCL++、NCCLX、ParallelKittens）普遍将**语义**（输入/输出约定）、**编排**（数据在何处、何时移动，即通信调度与同步）与**数据通路**（数据如何移动，即拷贝/归约的硬件实现）耦合在一起。
- **由此引发的三个具体问题**：
  - **问题 1（演进性与兼容性难以兼得）**：采用新传输机制（如 Hopper TMA）需要改动数据通路之外的部分；NVSHMEM 直到 2026 年才支持 TMA，比 Hopper 发布晚约四年；ParallelKittens 则只针对 Hopper/Blackwell，放弃仍在广泛部署的 Ampere。
  - **问题 2（新集合通信仍需显式编排）**：vLLM、SGLang、TensorRT-LLM 等常自研 AllReduce，但开发者仍须把语义手工翻译成编排，缺乏“可推导性”。
  - **问题 3（定制化被迫重访编排）**：应用需要控制归约顺序、按硬件调优、与计算融合（FlashMoE、MPK、MegaMoE），但修改数据通路往往牵连编排逻辑。
- **整体含义**：作者主张**将编排与数据通路解耦**——语义与编排在硬件代际间是稳定的，只有“如何搬字节”在不断演化；用固定中介接口隔离“不变”与“常变”，从而同时获得兼容性、演进性、可推导性与可编程性。

## 2. 方法论

### 2.1 核心思想：三层解耦栈

| 层 | 职责 | 具体内容 |
|---|---|---|
| 顶层：语义 | 做什么 | 用「输入布局 → 输出布局 + consume 操作」一行声明集合通信 |
| 中层：SNAC | 何处/何时 | Stage, Notify, And Consume 共享编排协议，从布局推导协调 |
| 底层：Atom | 如何 | 硬件相关数据通路，仅暴露 `copy` 与 `reduce<E>` 两个原语 |

### 2.2 关键技术与细节

- **布局抽象（三种）**：
  - `packed`：一段连续贡献（AllGather 的输入）；
  - `scattered`：按 rank 索引的连续分区（AllGather 的输出、ReduceScatter 的输入）；
  - `transposed`：rank 索引分区的交换（AllToAll）；
  - 每种均有变长 `V` 变体，分区大小运行时确定。
- **集合通信即布局变换**：`AllReduce = compose<reduceScatter, allGather>`（scattered→packed→scattered）；`compose<F,G>` 要求 F 的输出布局匹配 G 的输入布局，且融合为**单个 GPU kernel** 执行，避免冗余访存与两次 kernel 启动。
- **SNAC 协议流程**：
  1. **Stage**：各 rank 将应用缓冲区（无需注册）拷入注册的、对端可访问的内部 staging 缓冲区；
  2. **Notify**：以 release 内存序通知对端（packed 输入广播通知全体，scattered 输入按 rank 定向通知）；
  3. **Consume**：以 acquire 内存序等待通知后，通过 `Atom::copy` 或 `Atom::reduce` 从远端拉取。
- **编译期推导**：SNAC 是模板元程序，用 `if constexpr` 依据布局/consume 操作在编译期选择通知范围、输出地址计算与消费方式，避免关键路径上的运行时分支。
- **CTA 特化与分块流水**：将 N 个 CTA 分为 staging 组与 consuming 组；对 `compose` 再增加第三组 CTA。以 chunk 为粒度重叠 staging、归约与 gather（AllReduce 三组 CTA 流水）。
- **双性能路径（regime specialization）**：
  - **吞吐路径**：远程读（pull），实测带宽比 push 高至多 7%；
  - **延迟路径**：远程写（push）+ 将 8 字节 payload 与 8 字节 flag（epoch）打包成 16 字节原子包，将 staging 与通知合并为一次操作；实测 push 延迟低至多 1.98×，但因数据量翻倍仅用于小消息，交叉点由 codesign policy 决定。
- **Atom 统一流水线（prime / steady-state / drain）**：
  - 以 `cp.async` 从本地或对端 global 异步取数至 shared memory，多槽轮转；copy 与 reduce 共享同一流水线，仅“处理阶段”不同（写目标 vs 更新累加器）；
  - 未采用 TMA：实测 `cp.async` 在 256 KiB–1 MiB 快约 10–12%，且使用 LSU 而非 TMA 单元，便于与计算融合时避免争用；
  - **确定性归约**：每个输出元素单一累加器，严格按 rank 升序累加，E→FP32 累加后转回 E；另提供基于 `multimem.ld_reduce` 的交换机内归约作为可选路径（无固定顺序保证）。
- **BDP 驱动的流水线码设计**：`Q ≈ Rτ`，`Qcap = C·S·Bstage`；通过增加流水级数 S 或 stage 大小在固定 CTA 数下提升在途字节。表 3 给出 A100/H200/B200 的往返延迟约 2.2/2.1/2.8 µs，BDP 约 512 KiB/1 MiB/2 MiB。
- **实现**：CUDA C++20 header-only 库 + Python API（PyTorch symmetric 分配、JIT 编译）；SNAC 及其辅助 2,480 行，codesign policy 598 行；Atom 各代实现 53–299 行；循环 staging 双缓冲（每 GPU 2×256 MiB）+ 64 位 epoch 奇偶切换。

## 6. 主要结论与发现

- **集合通信性能**：七种集合通信上延迟最高加速 **5.14×**（B200 2 KiB AllReduce vs NCCLX）、带宽最高提升 **4.50×**（A100 2 MiB ReduceScatterV vs NCCLX）；相对 NCCL 的几何平均延迟加速 1.65–4.36×，带宽提升 1.05–1.53×。
- **资源效率**：`Atom::copy` 在 B200 用 16 个 SM 达到与 NCCL Device API 用 64 个 SM 相当的带宽；Purlin 集合通信在 32/148 SM 下 AllGather 718.7 GB/s、AllReduce 478.6 GB/s，超过用满 148 SM 的 ParallelKittens（710.9/483.9 GB/s）或与之持平。
- **流水线码设计**：固定 CTA 数下，流水线从 1 级增至 8 级使 B200 pull 带宽从 125 升至 761 GB/s（6.1×）；push 在 4 级即饱和（710 GB/s），pull 需 8 级，二者平台期不同，指导显存用量分配。
- **应用收益**：SGLang 离线服务吞吐与交互性平均 **1.13×**、最高 1.37×（低并发收益更大，A100 chat 并发 1 时 1.24×）；在线服务交互性平均 **1.26×**、最高 **2.85×**，最大增益出现在过载（1.5 req/s 时端到端 121.3 s→41.5 s）；扩散生成端到端延迟最多降低 **1.13×**。
- **质量无损**：AIME26 pass@16 与 majority@16 完全一致（96.67%），Qwen-Image 100/100 提示词像素级一致、ImageReward 相同。
- **少数劣势**：H200 上 1 GiB 大消息

- **少数劣势**：H200 上 1 GiB 大消息场景 Purlin 略逊于 NCCL（作者主动披露），推测与 staging 双拷贝带来的额外带宽开销、以及超大消息下流水线收益被固定开销摊薄有关；A100 因缺少 TMA/多播等新机制、NVLink 3 带宽较低，绝对收益幅度小于 B200。作者未回避这些不利数据，而是将其归因于设计取舍（通用性与可组合性优先），这一处理方式增强了结论的可信度。

## 7. 局限性、开放问题与作者披露的不足

- **域内限制**：全部实验限于单机 8 卡 NVLink 域，未验证跨节点（InfiniBand/RoCE）或 72 卡、576 卡机架规模的扩展性。作者将多机与更大 scale-up 域列为未来工作，这意味着 SNAC 的 Notify/Consume 协议在跨节点、非对称拓扑、部分连通场景下的正确性与性能尚无实证。
- **SM 资源占用与并发的权衡**：Purlin 集合通信虽只占 32/148 SM，但仍需与计算 kernel 共存；CTA 特化（staging/consuming/compose 三组）在小消息、低并发下可能出现组间负载不均，论文未系统给出各组 CTA 比例的自适应策略。
- **内存开销**：每 GPU 两个 256 MiB staging 缓冲区（合计 512 MiB）对显存紧张的部署（如长上下文、大 KV cache）并非无成本；论文仅称"可按需缩减"，未量化缩减后对带宽的影响曲线。
- **双路径切换策略**：push/pull 交叉点由 codesign policy 决定，但该 policy 的阈值推导依赖实测往返延迟与 BDP 表（表 3），换硬件需重新标定；论文未给出自动化标定流程或跨代外推的误差分析。
- **确定性与性能的取舍**：严格按 rank 升序的确定性归约限制了归约树的优化空间（如无法采用对数深度的分治归约）；交换机内归约路径虽快但无固定顺序保证，两者并存的语义边界需应用自行判断。
- **应用层证据强度**：离线实验每个配置仅一次完整运行，在线实验仅一个 trace、一种模型；虽然请求量大提供了统计稳定性，但缺少多 seed、多 trace 的方差报告，1.13× 这类平均增益的置信区间未给出。
- **对比覆盖的空白**：NVSHMEM 仅参与 peer-copy 对比而非完整集合通信对比；ParallelKittens 仅 H200/B200；缺少与 DeepEP、FlashMoE 等 MoE 专用通信库在 EP 场景下的直接对比，而 EP 恰是当前 scale-up 域的主要负载之一。
- **质量评估范围**：AIME26 与 Qwen-Image-Bench 分别覆盖语言推理与图像生成，但未覆盖长上下文检索、代码生成等对归约顺序敏感度不同的任务，质量无损的结论外推需谨慎。

## 8. 与相关工作的定位

- **相对 NCCL**：NCCL 以拓扑感知的 ring/tree 算法与高度调优的 kernel 取胜，但语义、编排、数据通路绑定于其内部实现，新增传输机制需改动核心；Purlin 以布局变换 + SNAC + Atom 的分层换取可组合性与跨代兼容，在延迟上优势显著、带宽上小幅领先，大消息极端场景偶有落后。
- **相对 NVSHMEM**：NVSHMEM 提供 PGAS 式 put/get 原语，是"数据通路"层的强手，但把编排责任留给用户；Purlin 的 Atom 层可视为对同类原语的规范化封装，并在其上补足了可推导的编排层。
- **相对 MSCCL++ / NCCLX**：二者通过 DSL 或图化方式生成定制 kernel，仍以"生成具体数据通路实现"为中心；Purlin 的差异在于固定中介接口、把变化收敛到 `copy`/`reduce<E>` 两个原语，使同一编排可跨 A100/H200/B200 复用。
- **相对 ParallelKittens**：ParallelKittens 深度绑定 Hopper/Blackwell 的 TMA 与集群特性，追求代内极致性能；Purlin 有意放弃 TMA（实测 `cp.async` 在 256 KiB–1 MiB 快 10–12%，且不争用 TMA 单元），以换取 Ampere 兼容与计算融合时的资源独立性。
- **相对应用侧自研 AllReduce（vLLM/SGLang/TensorRT-LLM）**：这些实现把语义直接硬编码为编排，难以复用与调优；Purlin 提供 Python API + JIT，使"一行声明"即可获得与手写实现相当或更优的性能，这是其可推导性主张的直接体现。

## 9. 启示与总体评价

- **核心贡献的判断**：论文最有价值的部分不是某一项微基准数字，而是"**语义/编排稳定、数据通路演化**"这一分层假设，以及用 `compose<F,G>` 把集合通信表达为布局变换、并融合为单 kernel 的实现路径。它把"新增一种集合通信"从改写数据通路降级为声明式组合，具备工程上的可复制性。
- **方法论的普适性**：SNAC 的 Stage–Notify–Consume 三段式与 release/acquire 内存序配对，是分布式同步的经典模式在此场景下的规范化；其价值在于把"何时通知谁"从布局自动推导（编译期 `if constexpr`），从而消除关键路径分支。这一思路可迁移到其他需要"应用缓冲区不入网"的通信场景。
- **性能归因的清晰度**：论文用流水线深度消融（B200 pull 1→8 级，125→761 GB/s）与 BDP 模型（Q ≈ Rτ）把带宽收益机制化，而非仅报告加速比；push 4 级饱和、pull 需 8 级的差异进一步指导显存分配。这种"机制—参数—性能"的闭环是其方法论上最扎实之处。
- **资源效率的实际意义**：16 SM 达到 NCCL Device API 64 SM 的带宽、32/148 SM 下比肩用满 SM 的 ParallelKittens，意味着通信可与计算真正共享 SM，这对 MoE、序列并行等计算密集负载的融合尤为关键。
- **需保留的审慎**：结论的适用范围应限定在单机 NVLink 域、所测三代硬件与所列七种集合通信；跨节点扩展、非对称拓扑、以及与 MoE 专用库的对比仍属空白。应用层 1.13×/1.26× 的平均增益幅度不大，实际部署收益取决于通信在端到端时间中的占比——论文在低并发与过载场景增益更大，恰好说明这一点。
- **总体评价**：这是一篇问题定义清晰、抽象层次得当、实现与实验相互印证的通信系统工作。它没有追求单项指标的最优，而是以"解耦"换取兼容性、演进性与可编程性的三者兼得，并用跨三代硬件的一致表现支撑了这一主张。其局限（域内验证、内存开销、策略需标定）属于工程落地层面的开放问题，不削弱核心论点的成立。
