## 摘要
稀疏混合专家（MoE）模型为 Web 应用提供了可扩展的容量，但不均衡的路由会造成计算与通信瓶颈。现有的放置与复制方法会重新分配这一工作负载，但额外的专家副本会与令牌相关缓冲区争夺有限的 GPU 内存。我们提出 LRMoE，一种内存感知的 MoE 训练系统，它联合重校准反向传播需求并平衡所保留的工作负载。在前向执行期间，它在资源约束下规划保留配额与专家放置，同时保留所有已路由计算。在反向传播期间，一种负载重校准度量会估计每个令牌-专家对（token-expert pair）对专家更新的贡献，并在这些配额内选择配对。一种容量感知的路由算法会将保留的配对分配到其原始专家的合格实例之间。随后，物理压缩形成更小的通信载荷和可变大小的分组 GEMM，从而降低反向通信量、计算量以及执行缓冲区需求。在 Qwen3-30B-A3B 与 GLM4.5-106B-A12B 上的实验表明，相对于 SYMI，LRMoE 将达到固定损失目标所需的累计 MoE 层训练时间减少了 21.2–44.8%。

## Abstract
Sparse Mixture-of-Experts (MoE) models offer scalable capacity for Web applications, but uneven routing creates computation and communication bottlenecks. Existing placement and replication methods redistribute this workload, yet additional expert copies compete with token-related buffers for limited GPU memory. We present LRMoE, a memory-aware MoE training system that jointly recalibrates backward demand and balances the retained workload. During forward execution, it plans retention quotas and expert placement under resource constraints while preserving all routed computations. During backpropagation, a load recalibration metric estimates each token-expert pair's contribution to the expert update and selects pairs within these quotas. A capacity-aware routing algorithm distributes retained pairs among eligible instances of their original experts. Physical compaction then forms smaller communication payloads and variable-size grouped GEMMs, reducing backward traffic, computation, and execution-buffer demand. Experiments on Qwen3-30B-A3B and GLM4.5-106B-A12B show that LRMoE reduces cumulative MoE-layer training time to fixed-loss targets by 21.2-44.8% relative to SYMI.

## 1. 核心问题与研究动机

- **背景**：Web 规模搜索/推荐服务依赖大模型，稀疏 MoE 通过“每 token 只激活少量专家”提升参数容量而不增加等比例计算。专家并行（EP）把专家分布到多 GPU，并通过 all-to-all 交换 token–expert 对（routed pair）。
- **核心矛盾**：路由是数据相关的，不同输入、层和迭代的配对数量差异巨大，导致专家计算与 all-to-all 流量在 GPU 间严重不均；同步执行按最慢参与者收敛，热点专家所在 GPU 成为 straggler。
- **现有方法的局限**：FasterMoE 影子专家、FlexMoE 动态放置、SmartMoE 混合并行搜索、SYMI/LAER-MoE 状态解耦、UltraEP/TopoEP 面向真实 post-gating 负载与拓扑——它们只改变“工作在哪里执行”，**不减少逻辑计算量**；复制出的专家副本还要与 token buffer 争抢有限 HBM，并带来状态搬运与梯度同步开销。
- **论文的关键判断**：存在两种性质不同的限制——
  - **聚合过载**：反向需求总量超过可用服务容量（论文给出必要性条件 Σ_e W ≤ Σ_g C_bwd）；
  - **空间不可行**：即使总量够，合法目的地受限、副本/暂存容量有界、单卡显存与网络路径约束也会使放置无解。
  - 图 1 显示：即使做 MILP 负载均衡，48/48 层仍全部超过单卡 262k pairs 的上限——**单纯“摊平”无法解决**。
- **核心洞见**：把反向需求视为**贡献感知的可调度变量**而非前向路由的固定后果，用“重校准（recalibration）”把 W 替换为保留需求 W̃ ≤ W，同时决定“保留多少”和“在哪里执行”。

## 2. 方法论

### 2.1 总体架构：两阶段解耦

- **前向阶段（决定“能负担多少”）**：路由确定逻辑专家与权重后，控制器统计各专家路由量 n_e，在 HBM、带宽、通信窗口约束下规划**保留配额 K_e** 与**副本放置**；随后执行**完整前向**并保存激活、专家中间量、路由权重、配对身份、参数版本。
- **反向阶段（决定“哪些对填充配额”）**：梯度到达后计算 LRM 分数，在每个专家内取 Top-K_e，再做容量感知重路由与物理压缩，最后执行变长 grouped GEMM。
- 设计要点：前向不打折（保证打分所需上下文与逻辑正确性），选择推迟到反向；配额在本次调用内固定，避免二次搜索。

### 2.2 负载重校准度量（LRM）

- 对被保护的专家投影（FC2）权重 W_e，配对 u=(t,e) 的梯度贡献是秩一外积：**G_u = (α_u·g_t)·φ_uᵀ**，其中 α_u 为路由权重、g_t 为上游梯度（未乘路由权重）、φ_u 为保存的投影输入。
- 省略该对的扰动 Δ_u = −G_u，用平方 Frobenius 范数度量，利用 ‖abᵀ‖²_F = ‖a‖²₂‖b‖²₂ 得：
  **R_u = α_u² · ‖g_t‖²₂ · ‖φ_u‖²₂**
- 三个因子分别对应：**路由强度**、**反向信号能量**、**专家状态幅度**；无需物化逐对权重梯度矩阵，计算代价低。
- **最优性**：附录 Proposition 7.1 用交换论证证明，在固定丢弃数、等行代价条件下，丢弃分数最小的 d 个（等价保留最大的 K 个）可最小化加性局部校准失真；按专家分区时该结论逐分区独立成立。

### 2.3 逐层配额准入（Algorithm 1）

- 候选保留率按**递减顺序**尝试（从全保留开始），每个候选联合求解配额 {K_ℓ,e} 与副本放置 Π，检查：放置可行、HBM 预算、通信时间 ≤ 重叠窗口。
- 可行性判定包含**完整前向负载及其保存状态**，不只是缩减后的反向需求；首个可行候选即固定配额与放置；若无候选可行则 admission 失败。
- 副本按“峰值行数”配置：保留后若某专家单卡可容纳，则**删除冗余物理副本**（示例负载 [4,2,3] → [3,1,2]），逻辑专家集合不变。

### 2.4 容量感知重路由

- 整数分配 X_eg：Σ_g X_eg = K_e，仅允许分配到该专家的**合格实例**（需具备对应参数版本与匹配的已保存上下文），目标是最小化**峰值 GPU 负载**而非均分。
- 重路由只改变物理执行者，不新增副本、不改变逻辑专家归属、不改变已准入的工作量；所需状态搬运计入资源核算。

### 2.5 物理压缩与变长 grouped GEMM

- 按目的地与专家实例，将保留的梯度行与对应激活/中间量按一致顺序打包，用 counts + prefix offsets 定义紧凑 all-to-all 载荷与 expert-major 张量段。
- 关键区别：**不是 zero-mask**（保留原 shape 时 GEMM 规模基本不变），而是真正缩减 FC1/FC2 四个反向 GEMM 的行维（数据梯度）与归约维（权重梯度），**无 padding**。
- 结果与 zero-mask 实现在相同保留集下等价（仅浮点差异）；逆映射把输入梯度 scatter-add 回原 token/槽位；副本参数梯度在逻辑 owner 处求和，每个逻辑专家一次优化器更新。

### 2.6 理论边界（作者自述）

- 单对恒等式精确；但多对同时丢弃时真实误差含交叉项 ⟨G_u, G_v⟩，仅在**成对正交**或**交叉项零期望**时等于加性目标，否则只有三角/Cauchy–Schwarz 上界。
- 该目标只是**局部投影梯度**量，不是非线性损失变化或优化轨迹的保证；等行代价假设下成立，不等字节代价会退化为背包问题。
