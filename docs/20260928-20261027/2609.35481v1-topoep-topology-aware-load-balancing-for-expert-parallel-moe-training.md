## 摘要
动态路由会在大规模专家并行混合专家（MoE）训练中造成严重的负载不均衡，使承载热门专家的 GPU 成为拖后腿的慢节点。由于每个 MoE 层都要等待最慢的 rank，这些慢节点会延长专家并行阶段并降低整体训练效率。现有专家并行负载均衡（EPLB）系统通常在 CPU 上计算负载均衡方案，这会引入设备—主机数据传输和跨 rank 同步，使得在每个层和每个微批次上进行调度都代价高昂。其规划模型也忽视了现代 scale-up 与 scale-out GPU 集群的分层通信开销。我们提出 TopoEP，一个面向大规模 MoE 训练的 GPU 原生、拓扑感知负载均衡系统。在每个 MoE 层和每个训练微批次中，TopoEP 将当前路由结果转换为热门专家复制与 token 重路由决策，并在不进行数据相关主机同步的情况下执行所得方案，从而降低关键路径开销。为生成这些决策，TopoEP 使用确定性的 GPU 求解器，先进行节点间放置，再进行节点内细化，使所有 rank 都能独立生成按位完全一致的方案。在 32 块 GPU 的 NVIDIA H800 集群上，将 TopoEP 与 Megatron-LM 集成后，在三个代表性 MoE 模型上使端到端训练吞吐量提升 6.2%--11.4%。

## Abstract
Dynamic routing creates severe load imbalance in large-scale expert-parallel Mixture-of-Experts (MoE) training, turning GPUs that host hot experts into stragglers. As each MoE layer waits for its slowest rank, these stragglers prolong the expert-parallel stage and reduce overall training efficiency. Existing expert-parallelism load-balancing (EPLB) systems commonly compute load-balancing plans on the CPU, incurring device--host data transfers and cross-rank synchronization that make scheduling at every layer and microbatch expensive. Their planning formulations also overlook the hierarchical communication costs of modern scale-up and scale-out GPU clusters.   We present \textit{TopoEP}, a GPU-native, topology-aware load-balancing system for large-scale MoE training. At each MoE layer and training microbatch, \textit{TopoEP} converts the current routing result into hot-expert replication and token-rerouting decisions and executes the resulting plan without data-dependent host synchronization, reducing critical-path overhead. To generate these decisions, \textit{TopoEP} uses a deterministic GPU solver that performs inter-node placement followed by intra-node refinement, allowing all ranks to independently produce bitwise-identical plans. On a 32-GPU NVIDIA H800 cluster, integrating \textit{TopoEP} with Megatron-LM improves end-to-end training throughput by 6.2\%--11.4\% across three representative MoE models.

# TopoEP 论文结构化总结

## 1. 核心问题与整体含义

- **背景**：MoE 通过 Top-k 路由只激活少量专家来扩展模型容量；专家并行（EP）把专家分散到多张 GPU，先 all-to-all dispatch 把 token 送到专家所在 rank，再由 combine 返回输出。
- **核心问题**：动态路由会使专家负载严重偏斜。论文实测 Qwen3-30B-A3B 的 48 个 MoE 层中，最大/平均专家负载比平均达 7.34（DAPO-Math）与 7.08（StarCoderData），峰值 12.93；且最热的 8 个专家在相邻微批次间有 15.9%–20.0% 发生更替。承载热门专家的 rank 因此成为拖后腿的慢节点，而每个 MoE 层必须等最慢 rank 完成，整体训练效率被拉低。
- **现有方案的不足**：
  - 系统级 EPLB（FasterMoE、FlexMoE、DeepSeek-EPLB）多在 CPU 上求解方案，需要在 gating 与 dispatch 之间做 GPU→CPU→GPU 往返（同步、D2H 拷贝、CPU 求解、H2D 回传），逐层逐微批执行时这些开销不可忽略。
  - 规划模型忽视现代集群的**分层通信成本**（节点内 NVLink 与节点间 RDMA 代价差异大），可能“负载均衡了但跨域流量暴涨”。
  - 较新的 GPU 原生方案（UltraEP、MoonEP）只针对单一 scale-up 域，不建模跨节点拓扑。
- **论文定位**：提出 TopoEP——GPU 原生、拓扑感知的在线负载均衡系统，**不改变 Top-k 选择、不损失模型质量**，在每层每微批把路由结果转成“热点专家复制 + token 重路由”方案并直接在 GPU 上执行。

## 2. 方法论

### 2.1 核心思想
- 每层 gating 后做一次 EP 组内 all-gather，得到全局路由矩阵 Ω=[ω_{s,e}]（源 rank s 选择专家 e 的分配数），所有 rank 拿到相同输入。
- 在 GPU 上用**确定性两阶段求解器**生成方案：先做**节点间（inter-node）放置**以消除跨域 token 流量，再做**节点内（intra-node）精化**以消除残余 rank 负载不均。
- 相同 Ω 与配置下，各 rank 独立算出**逐位一致（bitwise-identical）**的方案，无需协调者或方案广播，也无需数据相关的主机同步。

### 2.2 问题建模
- **决策变量**：x_{e,r}∈{0,1} 表示 rank r 是否承载专家 e 的实例（含主实例）；q_{s,e,r} 表示 (s,e) 分配在 rank r 上执行的 token 数。
- **约束**：
  - C1 token 守恒：Σ_r q_{s,e,r} = ω_{s,e}
  - C2 实例可达：q_{s,e,r} ≤ ω_{s,e}·x_{e,r}
  - C3 副本容量：每 rank 非主实例数 ≤ N_slot
  - C4 跨域副本判据：跨域放置副本需满足 ‖W_e‖ < 2·D_{dom(r),e}·S_tok（前向参数传输量小于暴露的远端 token 流量）
  - C5 主实例固定：x_{e,main(e)} = 1
- **目标**：最小化理想化暴露时间 T_comp + T_token + T_replica
  - T_comp = t_FFN · L_max
  - T_token = 2·S_tok·Σ c_{s,r}·q_{s,e,r}（按通信时间矩阵 C 加权）
  - T_replica = Σ c_{main(e),r}·‖W_e‖·x_{e,r}
- **净收益判据**：只有当 T_saved > T_plan + T_transfer 时，动态均衡才真正缩短训练时间。

### 2.3 两阶段求解器流程
- **Stage 1 节点间放置**：
  - 对每个域 d 计算复制收益 b_{d,e} = 2·D_{d,e}·S_tok − ‖W_e‖；正值表示“用一次参数传输换掉远端 token 流量”划算。
  - 各域独立地按收益降序把候选副本放到有空槽且负载最低的 rank 上。
  - 随后构造物理路由：优先选同域实例，否则使用该专家所有已部署实例，并把 ω_{s,e} 近似均分。
- **Stage 2 节点内精化**：
  - 每个 NVLink 域独立迭代：取最忙 rank r_b，对贡献其负载的专家评估同域目标 rank r_t（已有该专家实例或有空槽）。
  - 迁移量 δ = min(U_{e,r_b}, ⌊(L_r_b − L_r_t)/2⌋)，半差界保证不反转两者负载顺序。
  - 按迁移量、目标负载、通信代价排序择优；每轮只提交一次更新。
  - 只在同域内加副本，不新增跨域 token 路由，因此始终满足 C1–C5。
- **GPU 并行与确定性**：域间、源–专家任务间用 CUDA 线程块并发；节点内精化每域一个 block，用共享内存缓存放置与负载状态，warp/block 级规约选候选；确定性候选排序保证各 rank 结果一致。

### 2.4 低开销执行
- **副本缓冲管理**：每 rank 预分配固定数量副本槽并跨层复用；主实例保留模型/优化器状态与 checkpoint，副本只需 BF16 参数（每参数 2 字节，为完整 Adam 状态的 1/8）；反向时同一存储改为副本梯度。
  - 主参数缓冲 E/P·|W|、副本缓冲 N_slot·|W|、梯度累积缓冲 E·|W|（按来源 rank 分 P 个区）。
- **设备发起传输**：节点内用 TMA over NVLink，节点间用 NCCL GIN 单边 RDMA；缓冲区在初始化时注册到对称内存窗口，GPU kernel 直接用 window handle + peer rank + offset 寻址。
- **两 chunk 流水线**（c1、c2，计算流与通信流分离）：
  - 前向：dispatch c1 → 计算 c1 同时 dispatch c2 → 计算 c2 同时 combine c1 → combine c2；fill/drain 边界之外基本被隐藏。
  - 反向：缓存每层放置与槽映射，通信流预取参数；每 chunk 先 Dgrad 后 Wgrad 以便 token 梯度尽早进入反向通信；副本缓冲复用累积两 chunk 的 Wgrad，EP 组 fence 后主 rank 汇总。
  - 反向的重新拉参与梯度回传通常可被计算隐藏，主要暴露开销集中在前向的 T_plan 与参数传输。
- **实现**：约 10,000 行 Python + CUDA/C++，集成进 Megatron-LM，dispatch/combine 采用 DeepEP V2（commit af9a040）。
