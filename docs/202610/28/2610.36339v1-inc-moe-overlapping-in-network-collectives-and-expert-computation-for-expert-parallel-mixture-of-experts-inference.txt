Abstract 

In expert-parallel mixture-of-experts (MoE) serving, expert computation in each MoE layer is preceded by dispatch and followed by combine, both of which lie on the critical path: tokens must be dispatched to the accelerators that host their selected experts, and the expert outputs must be combined back at the token’s owner. The cost of these collectives can dominate layer latency, particularly in multi-node deployments, where inter-node bandwidth is far below intra-node bandwidth. We present INC-MoE, an expert-parallel MoE layer for the scale-out setting that offloads both communication phases to the network switch and overlaps them with each other and with expert computation inside a single persistent kernel. INC-MoE expresses dispatch as an in-network AllGather, realized by switch-side multicast, and combine as an in-network ReduceScatter, realized by switch-side reduction. We implement both collectives with message semantics, as message exchanges between the end hosts and the switch, and show that because the in-network AllGather and ReduceScatter load opposite directions of each link, running them concurrently reduces the bandwidth-bound communication time by N −22( N −1) relative to concurrent ring-based collectives, i.e., by 33% for four ranks and 43% for eight. On each end host, a single kernel partitions the tokens of a layer into bands and processes them through a three-stage AllGather–feed-forward network (FFN)–ReduceScatter pipeline. At steady state, role-specialized thread blocks gather the next band, execute expert computation on the current band, and reduce the previous band concurrently, thereby overlapping both collectives with each other and with computation, using entirely device-side synchronization. INC-MoE is a drop-in replacement for the MoE layer of vLLM. We evaluate it on a testbed that emulates a four-node scale-out deployment, in which a dedicated accelerator emulates an in-network computing (INC) switch. On prefill of OLMoE with four-way expert parallelism, INC-MoE reduces time to first token (TTFT) by up to 33% and increases throughput by up to 50% relative to vLLM’s default collective path, while matching its outputs. 

# 1 Introduction 

Mixture-of-Experts (MoE) architectures [10, 20, 28] decouple a model’s parameter count from its per-token compute by routing each token to a small subset of k expert feed-forward networks (FFNs) out of E. This sparsity has made MoE widely adopted in large language models [9, 24]. For large MoE models and throughput-oriented deployments, experts are often partitioned across multiple accelerators, potentially spanning multiple nodes, using expert parallelism (EP). Every MoE layer must then first deliver each token to the accelerators that host its selected experts ( dispatch ) and afterwards bring the weighted expert outputs back to the accelerator that owns the token ( combine ).

In the data-parallel attention plus expert-parallel FFN configuration used by serving engines such as vLLM [18], dispatch and combine are commonly expressed as two collectives: an AllGather 

(AG ) that makes every rank’s tokens visible to every other rank, and a ReduceScatter (RS ) that sums the partial expert outputs computed on each rank and returns to every rank the rows of its own tokens [4]. In the default implementation, the MoE layer executes in three sequential stages: an AG issued through the platform’s collective library [1, 2], a sequence of MoE compute kernels (e.g., alignment/permutation, two grouped GEMMs with an activation in between), and an RS .In the inter-node regime, where inter-node bandwidth is much lower than intra-node bandwidth, communication can account for a substantial fraction of MoE layer latency, making the layer communication-bound. This paper starts from two observations. First, the AG and RS formulation of dispatch and combine maps naturally to operations supported by a switch capable of in-network computing (INC): AllGather can be implemented through multicast, and ReduceScatter through reduction. INC for collectives has a long history in HPC [8, 12] and distributed training [19, 27], where it has been applied mostly to all-reduce invoked as a standalone collective (Section 2.3). Recent work has also explored in-switch support for MoE communication [30]. Second, offloading the collectives alone is not enough. In the bandwidth-bound regime, an in-network AG or RS taken in isolation completes in the same time as its ring counterpart, which is already bandwidth-optimal [6]: it still saturates one direction of each end host’s link (Section 3.2). The two in-network collectives, however, saturate opposite directions, so running them concurrently uses both directions of every link at once. By contrast, overlapping ring AG and RS does not reduce their combined bandwidth-bound communication time, since each collective already saturates both directions. Realizing this gain requires restructuring the MoE layer so that the AG and the RS are in flight at the same time, and so that expert computation proceeds while both are running. We present INC-MoE, an EP MoE layer for the scale-out setting built on these observations. INC-MoE offloads dispatch and combine to in-network AG and RS , and fuses the two collectives with expert computation into one persistent kernel that pipelines all three phases at sub-layer granularity. The tokens of the layer are split into bands ; while the expert FFN runs on one band, the switch is gathering the next band and reducing the previous one. Making this overlap effective raises three challenges that shape our design: 1. Fine-grained in-network collectives. The AG and RS must be issued and completed directly from device code at band granularity, with consistent message layouts and band boundaries across ranks despite unequal per-rank token counts. 2. Device-side synchronization. Gather, compute, and reduce thread blocks must coordinate data dependencies while progressing independently, and reductions must remain synchronized across ranks without introducing unnecessary serialization. 3. Pipeline balance and tail overhead. The relative costs of gathering, computing, and reducing vary with the workload, requiring an appropriate choice of band size and thread-block allocation. Moreover, the loss of overlap during pipeline fill and drain must be mitigated to minimize exposed communication latency. 2.3 In-network Collectives 

In-network computing (INC) executes collective operations in the switches of the fabric rather than on the end hosts [12, 19, 27]. A switch that can replicate an incoming message to several output ports implements a multicast, and a switch that can combine the payloads of several incoming messages implements a reduction. Compared with collectives executed by the end hosts, in-network 4collectives reduce the number of times data crosses the end-host links, replace the dependent steps of ring and tree algorithms with a single pass through the switch, and move the reduction arithmetic off the end hosts. Prior work has applied INC mainly to all-reduce, both in HPC [8, 12] and in distributed training [11, 19, 21, 22, 27]. Only recently has INC been considered for the dispatch and combine of expert parallelism [30, 33], and, to our knowledge, it has not yet been applied to expert-parallel prefill across nodes within a serving engine, the setting INC-MoE targets. Section 3.1 describes how INC-MoE builds AG and RS from multicast and reduction, and Section 3.2 analyzes their cost for expert parallelism. 

2.4 Device-initiated Communication 

In the host-side APIs of conventional collective libraries [1–3, 23], collectives are launched from the host as separate operations, which forces the host to sequence communication and computation. Overlap is then limited to the granularity at which the host can split the work into separate launches, and every additional split adds launch overhead and cross-stream synchronization. Fine-grained pipelining therefore pays a growing fixed cost per stage: a host-driven version of the band pipeline in Section 3.3 would require, for each MoE layer, one AG and one RS launch per band, interleaved with the expert kernels and ordered by events. Device-initiated communication [14, 15] removes the host from this loop. A running kernel can post transfers, signal peers, and wait on completions itself, so communication starts as soon as the data it depends on has been produced, at whatever granularity the kernel chooses, and without returning control to the host [5, 32]. This makes it possible to place communication and computation in the same persistent kernel. INC-MoE relies on this capability to issue the in-network collectives of each band of tokens from the device, overlapping them with each other and with expert computation inside a single kernel launch per MoE layer. 

# 3 Design of INC-MoE 

Motivation. Figure 2 illustrates how an MoE layer executes under the default vLLM EP path. Two inefficiencies follow from this execution. First, the three stages are serialized: the FFN cannot start until the whole AG has completed, and the RS cannot start until the FFN has finished on every token, so the full communication time is exposed on the critical path. Second, the collectives run on the end hosts as ring algorithms, which load both directions of every link equally. Each collective therefore saturates the link on its own, and overlapping the AG with the RS does not shorten their combined time (see Section 3.2 and Section 5.2). 

Figure 2: Execution of an MoE layer under the default EP path. Neither remedy suffices on its own. Offloading the collectives to the switch, by itself, leaves them serialized with each other and with the FFN. Overlapping endpoint collectives with computation, 5as in micro-batch overlap [29, 34] or fused kernels [5, 31], hides communication behind computation but does not shorten the communication itself. INC-MoE combines the two: the switch executes the collectives, which makes them overlappable with each other (Section 3.2), and the accelerator overlaps them with each other and with computation at the granularity of bands. 

Overview. Figure 3 gives an overview of INC-MoE. The EP ranks reside on different nodes and communicate over the scale-out network through a switch. The layer receives the hidden states of the rank’s tokens and the router output (selected experts and weights) from the serving engine and returns the combined output for the same tokens. Internally, it launches one persistent kernel per MoE layer. The kernel’s thread blocks are divided into three roles: gather blocks issue in-network 

AG s, compute blocks run the expert FFNs, and reduce blocks issue in-network RS s and complete them with a local reduction. The roles process the tokens band by band and hand data to each other through device memory. 

Figure 3: Overview of INC-MoE: pipelined communication–computation overlap (AG/FFN and RS/FFN) and communication–communication overlap (AG/RS) across bands. Dedicated thread blocks are specialized for AG, FFN computation, and RS, enabling concurrent execution of communication and computation tasks. 

3.1 In-Network AllGather and ReduceScatter with Message Semantics 

INC-MoE implements the AG and RS with message semantics . End hosts never read or write each other’s memory. Every transfer is a message exchanged between an end host and the switch, and the switch is responsible for replicating and reducing message payloads. This contrasts with memory-semantic designs, in which each end host writes directly into the memory of its peers [5, 32]. Combining message semantics with in-network computing enables the switches to deliver one incoming message to several destinations or to combine several incoming messages into one, in the scale-out setting. Figure 4 contrasts the resulting collectives with the ring algorithms used by the default path. 6End-host interface. The end-host side of the collectives is a client library callable from device code. A thread block posts an AG or RS on a region of a registered buffer, continues with other work, and later waits on the completion of that request. Posting a request does not move data on the accelerator: the network interface reads the payload from the registered buffer, transmits it to the switch, and writes incoming payloads directly into registered memory. In our deployment, messages are carried over RoCEv2 [13, 17]. The accelerator’s thread blocks are thus only involved where data must be prepared before transmission or processed after reception. The library also provides a cross-rank barrier. Each message carries, besides its payload, information that the switch and the receiving end host need to process it (e.g., the operation, the root, the byte range of the payload within the registered buffer, the address at which the receiver must signal completion). The end-host code depends on the switch only through this interface, so the same kernel can target any switch that implements the AG and RS message semantics. 

AllGather. The AG is built from rooted multicasts, one per rank. Each rank acts as the root for its own contribution: 1. The root sends its contribution to the switch as a single message. 2. The switch multicasts the message to the remaining N −1 ranks. 3. The network interface of each receiving rank writes the payload at the byte range given in the message and signals the completion address. All N ranks act as roots concurrently. A rank’s AG is complete once the contributions of the N −1remote roots have arrived. Its own contribution requires no network transfer. Each rank thus sends its contribution once, regardless of N , while a ring AG would forward the contributions of N −1ranks over N −1 sequential steps (Figure 4, top left). 

ReduceScatter. The RS is built from rooted reductions, one per output shard. Each rank is the root of the shard that holds its own tokens: 1. The N −1 non-root ranks send their partial results for the root’s shard to the switch, chunk by chunk. 2. The switch reduces each chunk as soon as all N −1 non-root ranks have delivered it, reducing different chunks in parallel. 3. The switch forwards each reduced chunk to the root as soon as it is ready, so arrival, reduction, and forwarding are pipelined. 4. The root adds its own partial result to the aggregated result locally, obtaining the final shard, and signals completion. Each rank therefore participates in N rooted reductions: as a sender in the N −1 reductions rooted at the other ranks, and as the root of its own. Because the root keeps its own contribution local, a rank sends N −1 shards instead of all N , and the switch reduces N −1 contributions per shard instead of N . A rank receives a single already reduced shard, whereas a ring RS would receive and reduce N −1 partial shards on the end host, one per step (Figure 4, bottom left). 

Data layout. Ranks own different numbers of tokens, but the byte ranges carried by messages must refer to the same elements on every rank. INC-MoE therefore lays out the gather and reduce buffers (on every rank) as N per-rank blocks of Tmax = max r Tr rows each, where rank r’s tokens 7occupy the first Tr rows of block r. The token counts of all ranks are known before the layer runs (vLLM tracks them for data-parallel execution), so every rank derives the same layout without exchanging metadata. 

Concurrent operation. The band pipeline (Section 3.3) keeps several collectives in flight at once, for example the AG of one band and the RS of an earlier band, and issues collectives of the same kind back to back. Completion signals are cumulative and compared against monotonically increasing per-operation thresholds (epochs) rather than being reset between operations, which removes the race between a reset and a late signal from the previous operation. 3.3 Overlap Kernel: Band Pipeline with Role-Specialized Thread Blocks 

Bands. INC-MoE splits each rank’s tokens into nb bands of β = ⌈Tmax /n b⌉ rows. Band j consists of rows [ jβ, min(( j+1) β, T max )) of every rank’s block, so a band covers a slice of every rank’s tokens and is self-contained for all three phases. The AG of band j gathers the j-th slice of every rank, the FFN of band j computes the partial outputs (Equation (2)) of exactly those tokens, and the 

RS of band j reduces them and returns to each rank its own j-th slice. All three roles and all ranks compute band boundaries with the same arithmetic. This invariant is essential for correctness: a single off-by-one difference between roles leads the reduce blocks to send rows the compute blocks have not written, or the compute blocks to read rows the gather blocks have not received. 9Role specialization. The kernel is launched with BAG + BFFN + BRS blocks, and each block determines its role from its index. Although the network interface performs the transfers, both communication roles do work on the accelerator. Gather blocks iterate over bands, copy the rank’s tokens of each band into the registered send buffer at the offsets of the padded layout (Section 3.1), post the AG of the band, and publish its completion. This work is light, so few gather blocks suffice. Compute blocks iterate over bands, wait for the corresponding AG , and run the expert FFNs of the band (Section 3.5). Reduce blocks iterate over bands, wait for the partial outputs of the band, post its RS , and, once the aggregated result arrives from the switch, perform the root’s local reduction: they add the partial sum received from the switch to the rank’s own partial results, in place in the rank’s block of the RS buffer Z, which then holds the final output. This local reduction is a memory-bound computation over the rank’s entire output, and it is the main reason the reduce role needs dedicated blocks. Each role advances independently at its own pace, as shown in Algorithm 1. 

Communication–communication and communication–computation overlap. At steady state, three bands are in flight at once: the gather blocks run the AG of band j+1, the compute blocks run the FFN of band j, and the reduce blocks run the RS of band j−1. The pipeline therefore realizes two kinds of overlap. Communication–communication overlap keeps an in-network AG and an in-network RS in flight at the same time, which is precisely the schedule that Section 3.2 shows to reduce the communication time from 2( N −1)  

> N

· SBW to SBW : the AG keeps the receive direction of each link busy while the RS keeps the send direction busy. Communication–computation overlap hides the expert FFN behind the two collectives. Because the gather and reduce roles are assigned to separate groups of blocks that progress independently, the two collectives overlap without any coordination beyond the per-band synchronization described below. 

Tail assistance. The overlap between AG and RS disappears at both ends of the layer. The AG 

of the first band runs before any RS can start, and the RS s of the last bands run after the final 

AG has completed. In this drain phase, the gather blocks sit idle, while the RS s of the last bands, including their local reductions, lie directly on the critical path. With tail assistance, gather blocks that have posted their last AG join the reduce blocks for the final ntail bands and take over part of their local reductions, so these bands are processed by BAG + BRS blocks instead of BRS . Tail assistance is most effective at large token counts (64K tokens per accelerator and above). Below that, its effect is small. 

Synchronization within an accelerator. Roles hand data to each other through flags in device memory written with release semantics and read with acquire semantics, so that a consumer observes all data written before the flag. Rather than gating each step on a barrier across all blocks, every block that produces work maintains its own monotonically increasing progress counter, and a consumer waits only on the counters of the blocks whose output it needs. In the reduce role, this lets each reduce block advance through its share of a band at its own pace, instead of preceding every reduction chunk by a barrier across the whole grid (which makes the slowest reduce block set the pace of all of them). Because counters only increase, they never need to be reset within a launch, which avoids reset races of the kind described in Section 3.1. 

Synchronization across accelerators. The RS of band j combines the partial outputs of all ranks, so reduce blocks on different ranks must not drift apart by more than one band. Empty bands. When ranks own different numbers of tokens, a band can be empty on some ranks, and a band can contain no rows routed to a given local expert. Blocks skip the work in these cases, but they must still advance every counter and participate in every barrier exactly as on the non-empty path. 3.4 Pipeline Configuration 

The throughput of the band pipeline is set by its slowest stage, and which stage is slowest depends on the number of tokens per accelerator. More bands shorten the fill and drain phases, during which 

AG and RS do not overlap, but add per-band fixed costs: collective latency, synchronization, and smaller GEMMs. The number of bands nb, the allocation of blocks to roles ( BAG , B FFN , B RS ), and the use of tail assistance were determined through an exhaustive empirical study, which swept these parameters across a range of per-accelerator token counts. The study showed that the optimal configuration shifts with the number of tokens per accelerator, as the balance between communication and compute changes. INC-MoE therefore applies the best-performing configuration for each token-count regime at runtime. The number of compute blocks is a compile-time parameter of the kernel, so each regime uses a kernel variant specialized for its compute allocation. 11 3.5 Fused Expert Computation 

For each band and each local expert, the compute blocks select the rows of the band routed to the expert and run two GEMMs: the gate/up projection with SwiGLU, and the down projection with router weighting. Experts are processed one after another within a band, and the compute blocks cooperate on the tiles of each GEMM. 

GEMM. Each (band, expert) pair is processed with two GEMMs implemented as device functions inside the persistent kernel, and local experts are processed one after another within a band rather than with a grouped GEMM. Each compute block is split into one producer group, which issues asynchronous bulk copies of operand tiles into a three-stage ring of shared-memory buffers, and two consumer groups, which issue asynchronous matrix-multiply instructions on filled stages and release them to the producer. Because the GEMM uses only block-local synchronization, it can be invoked by a subset of the kernel’s blocks while the remaining blocks run communication. Our implementation prioritizes communication efficiency over individually optimized GEMM throughput, reflecting the communication-dominated regime targeted by this work. Grouped GEMMs over the local experts of a band are a natural extension and would increase the margin by which communication dominates. 

Epilogue fusion. The gate and up projections are computed by one GEMM over the concatenated weight matrix, and SwiGLU is applied to the accumulators in registers in the epilogue, so that only the activated intermediate is written to device memory. The epilogue of the down projection multiplies each row by its router weight gt,e and accumulates the result directly into the token’s row of the RS send buffer Z. No separate weighting, scatter or staging step is needed between the FFN and the RS . Note that the RS buffer is zeroed at the start of each MoE layer, so that the contributions of a rank’s local experts accumulate correctly. 

Zero-copy output. The root’s local reduction leaves the final output for the rank’s tokens in place, in the rank’s own block of the RS buffer Z. Instead of copying these rows into a separately allocated output tensor, INC-MoE exposes that block to the serving engine as a tensor view, so the output of the MoE layer is consumed in place. The buffer is not reused until the engine has consumed the output. 

# 4 Implementation and Integration with the Serving Engine 

End host. The end-host side of INC-MoE consists of the fused kernel, the INC client library, and a launcher exposed to Python. Device-initiated communication is built on MSCCL++ [15]. 

Switch. The switch-side service implements the message semantics of Section 3.1. In our prototype, it runs on a dedicated accelerator attached to the scale-out network, which emulates an INC-capable switch. 

Serving-engine integration. INC-MoE replaces the MoE layer of vLLM at the boundary between the router and the expert computation. Routing (expert selection and weights) is delegated to the engine’s own routing function, so routing semantics, including normalization of the top-k weights, are unchanged. The per-rank token counts needed for the padded layout are taken from the engine’s data-parallel metadata. Model dimensions, the number of experts, k, the data type, and the EP 12 degree are runtime parameters. As a result, any MoE model whose experts are SwiGLU FFNs in fp16 or bf16 can use the layer without changes to the kernel or the model definition.

A hardware INC switch processes packets at line rate and can serve all roots concurrently, so we expect this dependence on message size, and most of the gap to the bound, to be largely reduced on switch hardware, as they are specific to the emulator rather than to the design.

# 6 Related Work 

MoE systems and EP communication. GShard [20], Switch Transformers [10], DeepSpeed-MoE [26] and Tutel [16] established the systems foundations of expert parallelism. For inference, DeepEP [32] and pplx-kernels [25] provide high-throughput and low-latency all-to-all dispatch and combine kernels, and MegaScale-Infer [38] disaggregates attention and expert computation across 15 devices. These systems optimize communication executed by the end hosts. INC-MoE instead offloads it to the switch and uses the AG /RS formulation of dispatch and combine [4]. 

Overlapping communication and computation. Flux [7] fuses communication into GEMM tiles for tensor-parallel layers. Comet [31] overlaps MoE dispatch and combine with expert GEMMs at fine granularity through dependency analysis and adaptive workload assignment. TileLink [35] and Triton-distributed [36] provide tile-level primitives and compiler support for writing overlapped kernels. FlashMoE [5] fuses the entire distributed MoE layer into a single persistent kernel with device-initiated one-sided transfers. At the system level, vLLM’s dual batch overlap [29] and SGLang’s two-batch overlap [34] split a batch into micro-batches so that one micro-batch’s communication hides behind the other’s computation. Like these works, INC-MoE splits tokens into slices that are processed in a pipeline. The split is confined to the MoE layer and runs inside a single kernel with role-specialized blocks. The communication it overlaps is executed by the switch, and it overlaps the two collectives with each other as well as with computation. Micro-batch overlap is orthogonal to INC-MoE and could be applied on top of it. 

In-network computing. SHArP [12] offloads reductions into switch hardware for HPC collectives, and SwitchML [27] and ATP [19] perform gradient aggregation on programmable switches for distributed training. The DeepSeek-V3 hardware study [33] argues for network hardware with native support for MoE communication patterns. Closest to our work, DySHARP [30] observes that existing in-switch collectives target static, regular patterns and proposes switch extensions for dynamic multicast and reduction, together with kernel fusion of the dispatch–compute–combine pipeline. MoE-Hub [37] places lightweight hardware in the GPU hub, the switch between a GPU’s on-chip crossbar and its scale-up links, to manage address allocation and data flow, so that producers can send data as soon as routing completes. Both propose new hardware for the scale-up fabric. INC-MoE takes a complementary position. It operates in the scale-out network with static AG 

and RS collectives, whose redundancy is small for top-k routing with large k relative to the EP degree (Section 2.2), and it focuses on the message-semantic collectives, their concurrent use, and the end-host pipeline needed to turn switch offload into end-to-end gains. 

# 7 Conclusion 

We presented INC-MoE, an expert-parallel MoE layer for the scale-out setting that executes dispatch and combine as in-network AllGather and ReduceScatter and overlaps them with each other and with expert computation in a single band-pipelined kernel. We implemented both collectives with message semantics using a device-side communication library and an accelerator-based emulator of an INC-capable network switch. We also showed that, because they load opposite directions of each link, overlapping both collectives reduces the bandwidth-bound communication time by N −22( N −1) 

relative to ring collectives. We integrated the layer into vLLM as a drop-in replacement. On OLMoE prefill with four-way EP in an emulated four-node scale-out configuration, INC-MoE reduces TTFT by up to 33% and increases throughput by up to 50% relative to vLLM’s default collective path. Our results show that switch offload and kernel-level overlap are complementary, and that combined they turn the communication bottleneck of expert parallelism into an opportunity for the network. 16 References
