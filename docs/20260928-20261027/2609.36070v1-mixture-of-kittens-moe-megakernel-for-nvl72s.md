## 摘要
AI 加速器系统正迅速整合为 scale-up 架构，其中数十到数千个 GPU 通过高带宽、单跳互连结构进行通信。我们发现，现有针对传统 scale-out 网络优化的混合专家（MoE）训练系统很难迁移到这一场景，其运行速度往往慢于使用 PyTorch 和 NCCL 构建的朴素基线。随着产业路线图指向更大的 scale-up 域，理解这一硬件范式的性能权衡正变得越来越重要。我们提出 Mixture-of-Kittens（MoK），一个为 Nvidia NVL72 设计的 MoE 训练系统。MoK 基于三项洞见来释放 scale-up 域的性能：(1) 针对每个算子选择基于 push 或 pull 的通信方式；(2) 重构计算与通信的重叠方式；(3) 完全消除 CPU-GPU 同步。MoK 将这些洞见提炼为单个确定性训练巨内核，融合了 token 分发、共享专家与路由专家的 FFN 以及 token 合并。在来自四个广泛使用的开放权重模型的 MoE 层形状上，MoK 的吞吐量最高可达最强公开基线的 $2.37\times$。在跨多个 GB300 NVL72 机架、使用 512 个 GPU 的生产运行中，MoK 将端到端训练吞吐量提升了 $1.41\times$。

## Abstract
AI accelerator systems are rapidly consolidating into scale-up architectures, where tens to thousands of GPUs communicate over high-bandwidth, single-hop fabrics. We find that existing Mixture-of-Experts (MoE) training systems, optimized for conventional scale-out networks, transfer poorly to this setting, often running slower than a naive baseline built with PyTorch and NCCL. With industry roadmaps pointing toward even larger scale-up domains, understanding the performance tradeoffs of this hardware regime is increasingly important. We present Mixture-of-Kittens (MoK), an MoE training system designed for Nvidia NVL72. MoK builds on three insights that unlock performance on scale-up domains: (1) choosing push- or pull-based communication per operator, (2) restructuring the computation-communication overlap, and (3) fully eliminating CPU-GPU synchronization. MoK distills these insights into a single deterministic training megakernel that fuses token dispatch, shared and routed expert FFNs, and token combine. Across MoE layer shapes from four widely used open-weight models, MoK delivers up to $2.37\times$ the throughput of the strongest publicly available baseline. In a production run on 512 GPUs spanning multiple GB300 NVL72 racks, MoK improves end-to-end training throughput by $1.41\times$.

- **现有系统失效**：主流 MoE 训练系统（DeepEP、HybridEP、Comet 等）针对 scale-out（InfiniBand/RoCE）优化，迁移到 NVL72 后性能不佳；论文实测**近一半配置下，PyTorch + NCCL 朴素基线反而优于所有被评估的替代方案**。
- **问题重要性**：MoE 已成为前沿模型核心组件，但在大规模训练中消耗**超过一半的端到端执行时间**；Nvidia 路线图指向 NVL144/576/1152，理解该硬件范式的性能权衡愈发关键。
- **核心研究问题**：如何从第一性原理出发，为 scale-up 域重新设计 MoE 训练系统，使通信、计算与调度开销同时最小化。

## 2. 方法论（MoK 系统）

### 2.1 总体思想

- 将 MoE 全部计算与通信（dispatch、共享/路由专家 FFN、gated activation、combine）融合为**单个持久化确定性 megakernel**。
- 以成本模型指导设计：
  $$C = \max(T_{comp}, T_{mem}, T_{comm}) + T_{non\text{-}overlap} + T_{sync} + T_{host}$$
  目标是同时压低各项并最大化重叠。

### 2.2 洞见一：按算子选择通信方向（push / pull）

- **机理**：细粒度重叠下，每个张量核任务必须等"数据已到达"信号才能启动，因此 `T_sync` 成为瓶颈。
  - push dispatch：每个 peer 都要发完成信号，signaling 开销 39–135 µs（占 dispatch 时间 8–18%），随 EP 度增长；
  - pull dispatch：只需 GPU 本地信号，signaling ≤ 4 µs。
- **选择策略**：让"接收信号的 GPU 同时发起远端 load/store"。
  - 前向：**pull dispatch + push combine**；
  - 反向：**pull reverse-combine + push reverse-dispatch**；
  - 通信-计算交接永不离开本 GPU，消除跨 GPU 信号。
- **调度表构建（Algorithm 1）**：单独 kernel 生成两列表 `{src_rank, src_index}`，行号即目标 buffer 位置；按 `(local expert ℓ, per-source-rank ordinal o, source rank r)` 排序——先按专家划分连续区域，区域内按 `(o, r)` 轮转交错以均衡网络链路，并连续填充本地 buffer。
  - 调度开销仅占 MoE 运行时间 **2.1–7.7%**，比 Comet 低 **1.4–2.2×**；
  - 同一张表可复用于四个通信算子（push combine 只需把 `{src}` 重解释为 `{dst}`）。

### 2.3 洞见二：重构计算-通信重叠（粒度可调）

- **粒度权衡**：minibatch 太小 → 张量核不饱和、每批固定开销累积；太大 → 首批 dispatch 与末批 combine 暴露。
  - 细粒度惩罚：$P_{fine}(b,w) \approx \lceil N_{routed}/b \rceil \, C_{ineff}(b,w)$
  - 粗粒度惩罚：$P_{coarse}(b) \approx T_{dispatch}(b) + T_{combine}(b)$
  - 吞吐最优 minibatch 跨工作负载为 **512–32,768 tokens**，不应在设计时固定。
- **最大化延迟同步**：通信**广度优先**（持续 dispatch 所有 token，不等计算），计算**深度优先**（一个 minibatch 跑完整个专家 FFN），双方仅在数据依赖处异步握手。
- **Kernel 融合**：单一 megakernel 内按 SM 分区（计算 SM vs 通信 SM），通过 GPU-local barrier 交互；避免每 minibatch 多次 kernel launch 与 stream 同步（数十 µs 级 `T_host`），也避免依赖硬件调度器保证并发。
- 效果：最优粒度相对最差粒度吞吐提升 **1.38×–3.53×**。

### 2.4 洞见三：完全消除 CPU-GPU 同步

- **动机**：NVL72 集成 CPU 上常见 PyTorch 操作比 DGX B300 慢 **1.46×–2.97×**；精确尺寸分配需把 token 计数拷回 CPU，丢 token 又损害训练质量。
- **设备端 token 环形缓冲（macrobatch）**：固定大小、读写重叠的生产者-消费者流水线（dispatch 写槽 3、FFN 处理槽 2、combine 读槽 1），大小作为可调参数；相比全量 over-allocation，仅增加 **1.7%** 几何平均延迟。
- **Ring-aware forward replay**：反向传播需重算前向中间激活，但 ring 会覆盖旧数据。MoK 将 ring 感知的 replay 融合进反向 megakernel，只恢复缺失中间量并与反向重叠；前向**按 macrobatch 逆序处理**，使结束时 ring 恰好全满，最大化存活 token、最小化 replay。

### 2.5 生产级附加特性

- **确定性**：固定浮点运算顺序，软件调度固定 atomic 顺序或用临时 buffer 按确定顺序归约，保证 bitwise 一致输出。
- **CLC（Cluster Launch Control）RDMA 重叠**：Blackwell 硬件原生 work-stealing，可让出 SM 给高优先级流的 FSDP all-gather，避免机架间通信被 megakernel 串行化。
- **MXFP8 支持**：共享专家保持 BF16 以稳定训练；预量化权重 kernel + 将激活量化融合进 dispatch、专家分组 GEMM 与 gated activation。
- **Router 权重梯度融合**：SonicMoE 风格，由 gated activation 与 down-projection 输入梯度的内积计算，融合进 gated activation 反向，避免物化 down-projection 输出。
- **共享专家**：不依赖 dispatch/combine，塞入第一个 dispatch 窗口填充计算 SM 空闲。
- **SM 分区可调**：前向、反向分别暴露通信 SM 数量作为调优参数。
